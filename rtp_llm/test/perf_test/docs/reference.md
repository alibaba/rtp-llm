# Unified performance test reference

`tools/perf_test` is the only supported performance-test command. Every new
run receives exactly one JSON config with these top-level fields:
`schema_version`, `model`, `engine`, `workload`, `execution`, `output`,
`regression`, and `publish`. Unknown fields, includes, interpolation, secret
values, and undeclared engine arguments are rejected.

## Capability matrix

| Mode | Backend | run | resume | profile | report |
| --- | --- | --- | --- | --- | --- |
| prefill | local | yes | yes | yes | yes |
| decode | local | yes | no | no | generated by run |
| prefill | aone, single machine or gang | yes | no | no | offline |
| decode | aone, gang only | yes | no | no | generated by run |

`--skip-test --run-dir=...` is the offline prefill `report` alias for local
and AOne runs. It rejects decode and any action other than `report`.

Prefill uses cache grids. Decode supports fixed input/global-batch grids,
materialized distributions, and bounded target-TPOT search with one scalar
`output_length`. The public entry also runs AOne single-machine prefill case
shards and multi-machine prefill/decode gangs. Ordinary Bazel single-machine
decode uses `backend=local` even when its test action runs on a remote GPU.
See [AOne execution](aone.md) for configuration, runfiles, and submit-host
requirements. Historical schema-v2 results and AOne execution plans remain
readable.

## Commands

Preview a local prefill run without filesystem or engine side effects:

```bash
./tools/perf_test --mode=prefill --action=run --config=rtp_llm/test/perf_test/examples/prefill_local.json --dry-run
```

Regenerate only derived charts and formula analysis from a completed prefill run:

```bash
./tools/perf_test --mode=prefill --skip-test --run-dir=perf_test_results/prefill-run
```

Preview a local decode run:

```bash
./tools/perf_test --mode=decode --action=run --config=rtp_llm/test/perf_test/examples/decode_grid_local.json --dry-run
```

`run` accepts `--config`. Follow-up actions accept `--run-dir` and reject config
overrides. Only prefill profile accepts `--cases`; omitting it selects every
planned case. Prefill run and resume write the offline charts and formula fit
report after formal results are finalized.

## Workload examples

`model.topology.tp`, `dp`, and `pp` default to 1. When `ep` is omitted,
it resolves to `tp * dp`, matching the engine's automatic EP derivation within
each pipeline stage. Explicit `ep` must equal `tp * dp`, or may be 1 when
`dp=1` for pure TP. The resolved value is recorded in the plan and fingerprint;
incompatible values are rejected before launching the engine.

The test-only batch scheduler uses a fixed 30-second cache-admission timeout per stream.
It does not evict or reschedule other streams to reclaim device KV blocks, so
a batch that cannot fit in KV memory could otherwise keep retrying indefinitely
when no request timeout is set. Once a stream times out, later streams in the
same selected batch get one state-machine attempt; those that cannot enter
RUNNING fail immediately without waiting. The timeout flag resets for the next batch.

Start with a JSON file in `examples/` and set model, tokenizer, topology and
devices for the execution host. Prefill supports generated cache grids,
`request_batches` with explicit groups, ordered named `grids`, and random or
traffic-sampled batches. See `prefill_grouped_local.json`,
`prefill_multi_grid_local.json`, `prefill_random_batch_local.json`, and
`prefill_traffic_distribution_local.json`. A batch larger than one requires
DP1. Sampled workloads freeze their cases before execution; `resume` uses the
saved plan without sampling again. Cached measurements seed requests before
the measured concurrent round, so throughput uses the full round duration.

Seeds run in concurrent batches of at most 8 requests. Each batch reserves
`cache_len + commit_tail_tokens + 1` tokens per seed against
`engine.max_batch_tokens`; the extra token reserves the output. When
`workload.workspace_tokens` is set, the sum of seed reservations rounded up
individually to physical cache blocks must also fit that limit. No separate
seed budget setting is required. Cold members need no seed. Each seed batch
uses its actual request count as the scheduler target, including the final
batch. All seeds must complete and pass validation before measurement starts;
a failed batch is fully drained and stops the case.

Sampled cases are checked together before execution for independent request and
cache-block IDs. Successful checks are reused for unchanged cases within the
same runner; a changed case or a standalone `run_case` still requires validation.
DashSC validates the actual token IDs without re-encoding every long prompt as
text. HTTP text transport keeps text/ID consistency checks. Prompt and seed
construction reuse verified tokenizer fragments, with initial full-sequence
verification and exact text-based fallback for incompatible tokenizers. Only
case fingerprints are retained across cases, not all prepared long sequences.
Internal token-sequence checks hash canonical little-endian signed int32 data
directly, avoiding long JSON strings. Out-of-range or non-integer token IDs are
rejected; persisted case fingerprints remain unchanged.

Decode examples cover fixed input/output/global-batch grids
(`decode_grid_local.json`), a materialized input-length distribution
(`decode_distribution_local.json`), and bounded target-TPOT search
(`decode_tpot_local.json`). DP splits each global batch across workers.
Target-TPOT results retain each attempted batch and the selected best batch;
an unmet target makes the run partial. Configuration, transport, validation,
and request failures stop that case; they are not treated as TPOT limits.
Optional inline profiling runs after
formal measurement and keeps its traces separate from measured results.
Heterogeneous decode lengths require one DP worker per frontend; the cluster
transport can route such batches across nodes. A frontend with multiple DP
workers accepts only uniform lengths. `worker_allocations` records planned
assignments, rather than observed request routing.

The local distribution example uses DP1. Planning rejects mixed lengths within
a frontend that owns multiple DP workers, before starting the engine.
If a decode capture may still be armed, its formal metrics are retained for
diagnosis but the case fails, subsequent cases are not executed, and the engine
shuts down. Such a run cannot become a completed baseline candidate. A manifest
write failure after a confirmed capture does not invalidate formal measurements.

Prefill profiling requires DP1. If an armed Kineto capture does not complete,
the session stops executing further cases and shuts down its engine; the
remaining cases are recorded as not executed because capture state is unsafe.

## Run directory

Each non-dry run creates one immutable directory below `output.result_root`:

```text
source_config.json
resolved_config.json
execution_plan.json
manifest.json
workload/
checkpoints/
results/cases.jsonl                 # prefill case records (latest record wins)
results/cases/<case_id>.json       # decode case records
results/result.json
results/summary.json
reports/
profiles/
traces/
.writer.lock                      # persistent owner metadata; flock owns the lock
```

The execution plan is frozen before model startup. Mutable
JSON artifacts are written atomically, and one writer lock protects each run.
New runs persist an absolute result directory. Follow-up actions verify that
`--run-dir` resolves to that same directory; moved or copied directories are
rejected rather than writing back into the original run. Older relative plans
must be opened from their original working directory.

Writer ownership uses a nonblocking filesystem `flock` held for the entire
action. The kernel releases it even when the owner is killed or crashes; the
metadata file remains and does not by itself indicate an active writer. Lock
errors include the file path, hostname, PID, action, and acquisition time.
The filesystem must support advisory locks shared by all writers.

Older schema-1 existence locks and incomplete metadata are not automatically
reclaimed. To recover one, first stop every action using that run and confirm
on the recorded owner host that its process has exited. Then remove only the
named run's `.writer.lock` and retry. Never remove a lock during a live action,
and never infer that a remote owner is dead from a PID check on another host.

Case IDs derive from normalized case identity and remain stable across ordering
changes. Formal results use the versioned common envelope; prefill and decode
metrics remain distinct payloads.

Prefill resume also verifies the engine fingerprint saved in its checkpoint:
the current production sources and Git revisions, plus content hashes of the
selected native libraries. Changing the checkout, sources, or build requires a
new run. Older checkpoints without this identity remain readable for reports
but cannot be resumed. The initial fingerprint reads available libraries once;
subsequent checks reuse digests only while their file identity remains unchanged.

For reproducible automation, set `PERF_TEST_REPOSITORY_REVISIONS` to a JSON
object mapping repository labels to full lowercase Git commit IDs (40 or 64
hexadecimal characters). The entry validates and stores this mapping as
`manifest.json.repository_revisions` before execution, including when execution
later fails. The launcher discovers the relevant checkout IDs; public code
contains no repository paths or discovery policy. Without the variable, the
mapping is empty. `BUILD_SCM_REVISION` remains the independent legacy
`manifest.json.code_version` value, defaulting to `unknown`.

Traffic-sampled prefill resolves its distribution file on the controller and
records the digest and sampling summary in `resolved_config.json`; the execution
plan contains frozen cases. Remote SSH hosts do not require the source file.
The accepted distribution can differ from the source due to bounds and batch
budget rejection; sampled lengths do not replay request arrivals.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | completed successfully |
| 2 | invalid CLI, config, or unsupported capability |
| 3 | invalid plan or unavailable resource |
| 4 | engine lifecycle failure |
| 5 | case failure or partial measurement |
| 6 | collection, report, regression, or required publisher failure |
| 130 / 143 | interrupt / termination signal |

## Manual SSH

The public SSH controller runs prefill and decode using an explicit host list.
It does not allocate machines. Prepare model/tokenizer paths, SSH access and
public build requirements on all hosts. See the benchmark guide for the YAML
controller config and local JSON workload contract.
Host, checkout and build options belong in the global `machine_config` and
`build_config`; benchmark overrides and search axes cannot change them.
Model sources belong in the JSON config. Host model options must match those
sources before downloads, so recorded model identity matches actual execution.

```shell
python -m rtp_llm.test.perf_test.multi_node.multi_benchmark -c rtp_llm/test/perf_test/multi_node/prefill_ssh_example.yaml
```

Rank zero measures and finalizes results; other ranks serve the distributed
model. The controller owns startup, shutdown, and artifact collection. Public
execution needs neither `internal_source` nor private Bazel configurations.
Regression and publisher fields remain parsed for schema compatibility; the
public run entry does not compare baselines or publish results.

The portable helpers are available independently of `run`: use
`rtp_llm.test.perf_test.regression.baseline` to parse/compare versioned
baselines or generate a candidate, `regression.golden` to write/validate a
versioned result golden, and `publish.policy` to persist required/optional
publisher outcomes. The explicit Bazel commands
`//rtp_llm/test/perf_test:{generate_perf_test_golden,validate_perf_test_golden}`
operate on finalized result files. CI chooses its accepted baseline and
publisher adapters; these helpers do not activate any gate or upload by
themselves.
