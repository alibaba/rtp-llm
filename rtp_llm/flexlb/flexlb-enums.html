① ReleaseReason 已删除：由实际流程决定资源处理

没有新增类、状态或方法。原有四个相关方法收敛为三个：finishUnpublishedRoute、rollbackSelectedRouteResources、cleanupRequest。

现有入口 职责
rollbackSelectedRouteResources(route) 撤销本次选址的 Encoder / Prefill / Decode 登记；Decode 已确认时不允许本地回滚。只回滚资源，不结束选址。
finishUnpublishedRoute(route, selection) 回滚本次资源后完成选址收尾。等待容量时可仅调用资源回滚方法，不提前结束仍需参与抢占的选址。
cleanupRequest(ctx) 请求进入 ENDING 且无进行中选址时，直接根据提交、远端释放确认和无反馈过期处理资源。已提交而释放依据不足时保留 Decode；未提交只释放未确认登记；超期清理本地登记不清除 Worker 上报占用。保留部分成功、通知和归档契约。

旧的 LOCAL_ROLLBACK 由回滚流程表达；REMOTE_CLEANUP / EXPIRED 由已有事实直接判断；COUNTERPART_FINISHED 兜底名不再存在；只被测试指定的 NOT_SENT 已删除，测试改为在真实 Endpoint 账本上验证结束清理和失败重试。

② 哪些含义近似、哪些应该合并

“建议统一”指复用同一业务词表并删除无意义的转换，不要求把两个枚举的所有值拼起来。以下区分源码已确认的对应关系与建议；除 ReleaseReason 移除外，以下跨类收敛尚未修改实现。

跨类枚举 / 值 关系、结论与建议
DecodeRequestStatus.Kind
↔ RequestEventType		 建议统一事件表达，优先级高。DecodeEndpoint.workerEventType 当前执行直接转换：CONFIRMED → ALLOCATED；TERMINAL + errorCode=0 → COMPLETED；TERMINAL + 非零错误 → FAILED。前者没有带来独立决策含义。建议 DecodeRequestStatus 直接携带已有 RequestEventType 的这三个值，保留精确 reservation 和 errorCode，限制合法组合，然后删除 Kind 和转换方法。不是删除事件身份或错误码，也不是把全部 RequestEventType 值无约束开放给这个对象。
DecodeEndpoint.CapacityFailure
↔ AdmissionRejectReason 		建议统一重复的拒绝原因词表，优先级中。BLOCKED_BY_HIGHER_PRIORITY ↔ HIGHER_PRIORITY_AHEAD；BLOCKED_BY_SAME_PRIORITY ↔ SAME_PRIORITY_AHEAD；INSUFFICIENT_CAPACITY ↔ RESOURCE_EXHAUSTED。但 CapacityFailure 另有 NONE 和 UNKNOWN_BLOCKER，AdmissionRejectReason.UNSPECIFIED 不等于明确的“来源未知”。因此不能直接用 UNSPECIFIED 吞掉 UNKNOWN_BLOCKER。可让内部容量结果携带公共拒绝原因，并明确表达未知来源；若扩展原因协议，需评估外部兼容。具体错误码仍在响应边界映射，不与原因枚举合为一个。
RequestEventType 的结束事件
↔ RequestContext.EndCause 的 Worker 子集 		相同事件在两层重复命名，适合进一步收敛；不建议合并整个枚举。workerEnd 中 COMPLETED → WORKER_COMPLETED、FAILED → WORKER_FAILED、PRIORITY_CANCELLED → PRIORITY_PREEMPTED、ENDPOINT_CLOSED → ENDPOINT_CLOSED。RequestEventType 还含活跃、资源分配、远端清理；EndCause 还含本地发布失败、请求截止、调度器关闭等。建议在结束处理边界直接解释已有 Worker 事件，避免构造只换名字的中间事件；保留本地结束原因。是否还需归一化历史原因，应按实际查询/归档消费者核对后决定。
EngineGrpcClient.CancelReply
↔ RequestEventType.REMOTE_FENCED / REMOTE_CLEANED 		部分保证相同，保留协议边界。REQUEST_FENCED / REQUEST_CLEANED 对应业务上的远端阻止后续入队/确认清理。CancelReply 另外有 ACCEPTED、NOT_FOUND、FAILED，不能全部转为成功业务事件；同一保证也可能来自不同反馈通道。建议集中做一次协议解释，不将 RPC 回复类型直接扩散成资源状态。尤其 ACCEPTED 与 REQUEST_CLEANED 绝不能合并。
CancelReason
↔ EndCause
↔ ReleaseReason		 均带“原因”，但不是同一事实，不合成通用 Reason。CancelReason 记录取消的触发来源；EndCause 记录结束证据/来源；ReleaseReason 当前实际控制资源清理策略。客户端先取消后 Worker 完成可同时发生，不能丢失其中之一。应重点移除 ReleaseReason 对既有事实的重复编码，而不是向它追加更多结束原因。
RequestContext.ResponseKind
↔ RequestFuture.Completion 		同有取消，但不合并。ACK / TERMINAL / CANCELLATION 表示响应候选的用途；RESPONSE / FAILURE / CANCELLATION 表示 Future 的完成通道。ACK 和 TERMINAL 都可能通过响应值完成；一个错误响应也不一定通过异常通道完成。两者不是同一分类。
WorkerEndpoint.RegistrationPhase
↔ DecodeResources.RegistrationState 		词面相近，不合并。REGISTERED / COMMITTED 表示登记是否已提交；NOT_REGISTERED / UNCONFIRMED / CONFIRMED 表示 Decode 是否存在登记及是否得到引擎确认。提交不等于确认。若二值提交阶段改为布尔属性，也应独立于引擎确认事实，不增加一个包含全部组合的总枚举。
RequestRepository.RegistrationResult
↔ WorkerEndpoint.RegistrationStatus
↔ WorkerEndpoint.CommitStatus 		均为登记/提交结果，但对象不同，不合并。请求仓库检查 ID、上下文绑定；Endpoint 接纳检查容量、快照版本及端点可用性；提交检查具体登记身份及提交条件。统一成一个大 Result 会让每个消费者看到大量不可能出现的值。
WorkerStatus.CloseReason
↔ AbstractGrpcClient.CloseReason 		只有 DISCOVERY_REMOVED 相同，不合并。前者关闭 Worker 状态跟踪，还可因连续失败触发；后者关闭连接客户端，还区分替换、整体关闭与重复实例丢弃。对象和生命周期不同。同一发现删除事件可导致两个对象关闭，不代表它们共用一个关闭状态。
CacheMatchMode
↔ CacheMatchSource		 LOCAL_SYNC / KVCM 重复，但不合并。Mode 是配置的主方式；Source 是本次结果的实际来源，还含 LOCAL_STANDBY。配置 KVCM 时结果可来自备用本地；若合并，会把“想用什么”和“实际用了什么”混在一起。
StrategyErrorType / BalanceStatusEnum / StatusEnum
↔ GrpcFailure.Kind / Proto ErrorCode 		都有超时/连接失败/内部错误，不做全局错误枚举。分别服务调度响应、状态同步、公共异常映射、异常根因诊断和外部协议。保留边界映射与数值兼容，不从对外错误码反推内部事实。另有独立问题：StrategyErrorType.NO_ENCODER_WORKER 与 VIT_ROUTE_STALE 都是 8408，数字冲突应单独处理，不能把它们当成同一语义合并。
ApiMetricsReporter.Event
↔ ZkMasterEvent		 部分上下线里程碑接近，不合并。前者记录指标里程碑，后者驱动主身份、连接及服务生命周期；指标完成点不必等于触发事件。可复用真实事件生成指标，但不让指标词表反过来控制生命周期。
GrpcCallTrace.Stage / EndpointTrace.Stage
↔ GrpcTransportObserver.Event 		RPC 与连接词语相近，不合并。调用阶段、Endpoint 同步打点、底层传输异常分别具有不同粒度；一次 Endpoint 轮询可包含多个调用/锁事件，一条连接也可服务多次调用。保持追踪关联，而不是共享一个 Stage。

重点证据：DecodeEndpoint.workerEventType；DecodeStrategy 容量失败映射；RequestContext.workerEnd / selectResponse / recordCancellation。

③ State / Phase：相似的“阶段”到底在描述谁

类型 准确对象与应保留的边界
RequestPhase 业务工作种类：编码还是生成。不是排队、运行、清理阶段。
RequestState.State 对外查询的进展/最终结果。RequestState.from 优先取已有归档结果，其次最终结果，再次取消请求，再按路由是否提交区分已接纳/排队。属于派生视图，不应另维护一套可独立写入的进行中状态。
RequestContext.Phase 上下文是否还开放、正在结束、已归档。phase() 根据归档记录和 endState 派生，并非另一份可变状态字段。对外显示 CANCELLED 时内部仍可处于 ENDING 等待清理；不能和查询状态合并。
ResponseCompletionExecutor.Registration.Phase 一个响应完成任务的执行器进度，不是请求进度。任务已 COMPLETED 仍不代表请求远端资源已清理。
TaskPhase ↔ DecodeTaskPhase TaskPhase 是引擎上报阶段；DecodeTaskPhase 是 Master 用于抢占成本/取消方式判断的分类，额外表达本地预留、未交付、引擎可能已看到等不确定状态。RUNNING 有相同观察基础，但不能把 MASTER_QUEUED_NOT_DISPATCHED 塞进引擎协议枚举；映射应在持有本地登记和引擎观察的边界集中生成。
PriorityPreemptionProgress 一次抢占取消的进展，不是引擎运行状态，也不是资源全部释放的证明。是否能从已有取消操作派生需继续沿具体持有者核对，不能只因为有 CANCELED 就复用 RequestState.CANCELLED。
WorkerEndpoint.EndpointState 端点是否接纳及端点自身清理阶段。与请求上下文的 OPEN / ENDING / CLOSED 是不同对象，不能因为都能关闭就统一为一个 LifecycleState。

审核顺序：先确定对象与事实 → 找权威维护位置 → 判断是否可派生 → 仅在必要边界转换 → 删掉同义类型与中间转换。不是按每个类各配一套 State / Phase，也不是机械要求所有阶段共用一个枚举。

④ 完整生产枚举清单

如何理解“互斥”：Java 的一个枚举变量只能保存一个值，但这不代表对应的业务事实只能发生一种。

状态互斥：同一对象同一时刻只处于一个状态，之后可以转换。结果单选：一次操作只返回一个分类，但多个失败条件可能同时成立。事件可共存：同一请求或同一轮操作可以先后产生多个事件。语义重叠：存在包含关系、兜底类别或混合分类维度。

所有“互斥”判断均限定具体对象、时刻或单次操作；不是说这些值在整个系统中不能同时出现。分类原则和设计判断是结合定义与调用代码得出的分析。
