# FlexLB 开发与审核入口

先识别用户要求设计、实现还是 review，再读取对应规范。入口只负责选择规范、确定范围和项目验证，
不另写一套设计或实现标准。用户只要求解释、方案或审核时不修改代码。

## 根据任务选择规范

| 任务                                   | 读取的规范                                                 | 工作边界                                                                             |
| -------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 流程设计、跨组件职责和协议调整         | [workflow-first-design](../workflow-first-design/SKILL.md) | 明确行为契约、状态与资源归属、失败处理和验收；需要落地时继续读取实现规范。           |
| 功能开发、缺陷修复、重构、局部代码修改 | [class-implementation](../class-implementation/SKILL.md)   | 沿实际调用落实类和方法；发现必须改变跨组件契约时，再读取设计规范。                   |
| 代码 review、设计与实现一致性审核      | 上述两份规范都读取                                         | 对照设计职责和实现约束检查当前代码；不新增第三套审核标准，也不强迫局部修改重做架构。 |

[术语表](references/terminology.md) 独立维护命名与业务含义。涉及类名、方法名、状态、资源或流程术语时查阅，
它不是另一套开发流程，也不要求为每个术语创建类型。

规范统一维护在仓库 `rtp_llm/flexlb/skills/`，不依赖个人技能目录的副本。
仓库根目录 `.agents/skills/flexlb-development` 只链接到本入口；设计与实现技能由入口按需读取。

## 确认工作范围

- 阅读适用的 `AGENTS.md`，检查当前分支、暂存区和工作区，区分已有改动与本次任务。
  以真实代码、调用方和用户当前要求为依据；旧行号、旧报告不能代替源码证据。
- 先确定要改变的行为及必须保持的契约。命名、排序或排版任务不夹带生命周期和重试策略变化。
  参考类名、模块目录及命令以所在分支的实际代码为准，不为统一规范顺带迁移整个分支。
- 先沿入口追到主要副作用、异步交接和清理出口，再实施或评审。不同角色和模式按实际支持范围核对，
  不能遗漏 Encoder，也不能强迫它采用虚假的 P/D 状态或取消 RPC。
- 架构改变时同步更新相关现有架构说明；局部修复不主动创建新设计文档。
  不覆盖其他会话的改动，不全量暂存无关文件。

## Review 如何执行

1. 标明审核基线或当前工作区，读取实际 diff、相关实现、调用方和测试；截断输出不算读完。
2. 按设计规范核对谁决策、谁保存事实、谁执行副作用、何时交接、失败后谁清理。
   依赖改为接口或回调后仍须追踪实际访问能力，不能只看类型宣布解耦。
3. 按实现规范检查命名、字段用途、方法效果、最小可见性、校验位置、状态转换、
   精确身份、资源释放、局部并发及被替代代码的清理；类说明必须对应真实流程。
4. 对可能的问题构造具体触发场景，必要时运行有区分力的测试。区分源码确认、
   并发交错推演和实际复现；测试通过、类数减少、成员排序通过都不能单独证明设计正确。
5. 先报告可确认的问题，说明位置、触发条件、影响及对应规范；建议只覆盖必要修改。
   没有明确问题时如实说明，同时列出验证范围和未验证部分，不凑问题，也不把猜测当结论。

需要复杂度审核时，直接使用设计规范检查流程和协议、实现规范检查类和控制流。
不额外维护 review 专用规则或只为转调建立独立技能。

## 项目验证与提交

- 从 FlexLB 目录使用 Maven Wrapper，按风险运行相关 UT；行为和生命周期重构先固定基线，
  再补必要的契约测试。用户要求先加红测时保留红测，不提前修实现。
- 默认 `./mvnw test` 包含功能和性能回归；不跳过性能标签、放宽阈值或修改断言换取通过。
  纯命名、注释和格式修改不机械新增行为测试。
- 代码修改完成前运行整个 reactor 的 `./mvnw spotless:check -Pspotless-check`。
  成员顺序按仓库 `tools/order_java_members.py` 检查；修改检查脚本时运行其回归测试。
  模块级格式检查不能代替全量结果，格式修复仅限授权范围。
- 提交前在仓库根目录运行并通过 `python3 -m pre_commit run --hook-stage pre-commit`，
  检查本次暂存内容。首次使用安装 pre-commit，并设置 `git config --local core.hooksPath .githooks`；
  普通 `git commit` 继续执行 hook，不通过 `--no-verify`、`SKIP` 或停用 hook 绕过失败。
- 检查失败时区分回归、基线问题、测试契约和环境干扰。共享工作区变化时限定自己的差异，
  必要时用隔离副本验证，说明与当前工作区的区别，不持续接手无关失败。
- 提交遵循 Conventional Commits，只包含已授权的改动；纯格式提交不得夹带功能修改。
  不因提交需要擅自清空暂存区、改写历史或推送。
- 交付说明实际行为变化、规范归属、执行过的验证及剩余限制。
  区分读过源码、测试通过和真实环境验证，不能将局部结果描述为全量验收。
