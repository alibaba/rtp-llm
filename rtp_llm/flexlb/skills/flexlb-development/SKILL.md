# FlexLB 开发规范

让了解业务但首次接触该类的人，能从代码和相邻注释直接读懂流程、状态及清理责任。
以真实代码和用户当前要求为依据；简单修改直接落实，不为套流程扩大任务。

## 统一术语与命名

新增、修改或审核类名、方法名、字段名、状态名及架构说明时，读取
[FlexLB 开发术语与命名约定](references/terminology.md)，按业务含义选择术语。
重点区分调度、选址、路由发布、交付、抢占、取消、资源释放和请求清理，不能互相替代。
同一个概念使用同一个词；不同含义使用不同名称，不用 `Placement` 等宽泛词统称多个步骤。
术语表中的现有类名是定位示例，不是新增抽象的要求；旧名迁移只处理当前授权范围，
不能机械替换无关的缓存淘汰、外部协议字段、配置键或监控指标。

## 目录与文件归属

源码按七个独立 Maven 业务模块组织，根包与模块一一对应。
新增、移动文件先确定业务归属，再核对实际编译依赖；完整目录见
[架构总览](../../docs/architecture/00-overview.md)。

| Maven 模块 / Java 根包       | 职责                                                       |
| ---------------------------- | ---------------------------------------------------------- |
| `flexlb-api` / `api`         | FlexLB 应用入口、装配、对外服务及调度协议。                |
| `flexlb-config` / `config`   | 配置定义、来源、解析、合并与校验。                         |
| `flexlb-balance` / `balance` | 调度、队列、路由选择、请求生命周期及清理。                 |
| `flexlb-worker` / `worker`   | Worker 身份与状态、Endpoint 账本、状态同步及 Engine 通信。 |
| `flexlb-cache` / `cache`     | 缓存匹配、索引、反馈和 KVCM 集成。                         |
| `flexlb-master` / `master`   | 主节点选举、主地址查询和变更通知。                         |
| `flexlb-util` / `util`       | 公共组件、连接、服务发现、常量及通用定义。                 |

- `RequestScheduler` 和具体调度器放 `balance.schedule`；与调度共享身份和状态提交边界的
  RequestContext、Repository、Lifecycle 同包维护。队列实现放 `balance.queue`，
  选址放 `balance.strategy`，外部路由查询放 `balance.request`。
- Worker 公共身份留在 `worker`，请求记录、资源账本和资源协作接口放 `worker.endpoint`；
  状态对象、轮询更新及其指标放 `worker.status`，远程调用放 `worker.rpc`。
  Worker 缓存状态与更新信息放 `worker.cache`；
  缓存匹配和索引逻辑放 `cache`，KVCM 集成放 `cache.kvcm`。
- 配置按“找什么配置、配置怎么加载”组织：总配置 `FlexlbConfig` 和 `ConfigService`
  留根目录；调度、排队、抢占和请求超时放 `config.scheduler`，选路放 `config.routing`，
  Worker 管理放 `config.worker`，缓存与 KVCM 放 `config.cache`，指标/日志/追踪放
  `config.monitoring`，主选举放 `config.master`，模型服务/角色/地址/分组放 `config.service`。
  加载、合并、校验放 `config.loading`，来源放 `loading.source`，解析和旧版转换放
  `loading.parser`，`FlexlbConfigMerger` 直接放 loading，不另建只有一个类的 merger 目录。
- 通用连接池、调用机制放 `util.network`，服务发现复用 `util.discovery`；
  公共常量和通用定义可放 util，业务专用常量、异常和状态跟随所属业务。
  发现组件只消费通用地址及配置，不引用 Worker 或请求账本。
- 目录用具体对象和用途命名，不使用含义不明的 `client`、`model`、`optimizer`、
  `observability`，也不按 HTTP/gRPC 将各业务重复分目录。协议差异体现在类名。
  不同业务尽量不用同名子目录；`trace`、`log`、`metrics` 等职责明确一致时可以重复。
- 生产依赖方向为 `api → balance → cache → worker → master → config → util`，
  可跳级依赖所需的底层模块，禁止反向引用和环。底层确需上层提供数据或行为时，
  由底层定义实际需要的窄接口，上层实现，在 api 装配；不能为了搬目录复制状态、
  增加无业务用途的中间对象，或把业务实现塞进 util。测试依赖也不能反向成环。
- 包间只开放真实协作接口，不为测试放宽生产可见性。UT 与 testFixtures 跟随被测模块和
  包；依赖完整应用装配的集成测试放 api。迁移前检查同名文件，逐份保留有效用例，
  不用覆盖文件完成合并。Mock Engine 是独立测试工具。
- 移动时同步修改 import、全限定类名、反射入口、启动类、脚本、日志配置和现有架构文档。
  Engine、调度和 KVCM 协议分别由 worker、api、cache 生成；wire package、字段号和 RPC
  方法属于兼容边界。生成文件、target 和编译缓存不参与手工源码迁移。

## 开始修改前

本技能及相关开发技能统一维护在 FlexLB 的 `skills/`，以仓库版本为准。
仓库根目录的 `.agents/skills/flexlb-development` 通过相对符号链接指向本技能，
让仓库根目录、`rtp_llm` 和 `rtp_llm/flexlb` 下的 Codex 都能发现同一入口。

- 从当前工作区定位 `rtp_llm/flexlb`，阅读适用的 `AGENTS.md` 和相关模块说明。
  这些文件是仓库约定的来源；本技能不固化会随重构变化的类名、配置项或模块职责。
- 查看工作区和暂存区，区分用户既有改动与本次任务。不能通过恢复文件、整文件覆盖或
  全量暂存清理别人的改动；基于当前代码修改，不假设工作区等于 HEAD。
- 阅读实际入口、关键调用方、被改类及相关测试。架构问题按需阅读
  `docs/architecture/` 和当前适用的设计说明，区分设计目标、历史提案和已实现行为。
- 先明确要改变的行为与必须保持的语义。用户只要求解释、评审或方案时不直接改逻辑；
  只要求命名、排序或排版时不顺带修改生命周期、重试或同步策略。
- 跨模块职责调整按需读取 [workflow-first-design](../workflow-first-design/SKILL.md)，
  局部实现按需读取 [evidence-first-implementation](../evidence-first-implementation/SKILL.md)；
  不把小修改强制升级成架构设计。

## 从业务路径判断设计是否直观

重构讨论先回答“谁调用、什么条件下调用、提交的是什么任务、由谁结束”，再决定类和接口。
沿实际请求走一遍入口、选择、排队、交付、失败及清理；不能只解释每个局部函数合理，
却让完整链路依赖多层转调、反向调用或隐藏的状态配合。复杂流程精简时读取
[flow-complexity-review](../flow-complexity-review/SKILL.md)。

- **配置组合必须能看出执行路径。** 调度时机、批次选择、路由发布或发送请求是不同问题，
  但把它们拆成几个枚举并不自动带来清晰设计。明确有效组合、各自入口及最终执行者，
  核对同一提交函数为何被多处调用、不同模式是否绕过了应有的负责组件。
- **特殊角色先判断能否使用已有流程。** 例如 encoder 没有 P/D 阶段，不意味着必须新增
  一套生命周期；先确认差异能否由角色能力和阶段配置表达。共用流程也不能强迫 encoder
  构造虚假的 P/D 状态。是否批次交付、是否返回路由，应按实际配置契约判断。
- **共同动作通过共同接口调用。** 例如请求过期清理，管理者遍历已登记实例并调用统一入口，
  各实现负责自己的记录、TTL 和释放规则；不要在管理者中列举角色、强转类型或复制调用链。
  只有确实没有相应资源的实现才可不做处理，不能用默认空实现掩盖遗漏。核对角色注册表、
  创建和清理路径是否都覆盖已支持的角色；角色可用于指标标签，不应成为共同动作的分派依据。
- **类拆分服从整条链路的理解成本。** 主流程、模式实现和引擎通信应有清楚的责任边界；
  继承或组合要让差异集中，不能只是把分支和转调分散到更多文件。用户给出的类数上限
  按完整链路统计，不靠换包、改名或塞进内部类规避。具体数量约束保留在适用方案中，
  不把某一次设计的类数上限固化为通用开发规则。
- **先消除协议，再修补分支。** 若一次操作需要多处设置标志、反复登记和撤销、来回通知，
  先追查责任交接是否重复。新增状态或辅助类时必须说明它保存的独有事实，以及替代并删除
  哪套旧机制；不要在旧机制上不断叠加兼容入口和补偿路径。
- **同一业务动作集中提交。** 沿调用链检查登记、容量检查、入队或释放是否被拆成只会连续
  调用的多层接口。同一次持锁即可完成的操作优先合并，不让上游搬运中间结果、再次领取许可
  或重复加锁。创建和后续更新若遵守同一状态发布契约，应共用更新入口；确有不同原子边界、
  失败语义或异步交接时才保留分段，不为尚无依据的性能优化维护两套流程。

## 从读代码的疑问追到职责和契约

遇到“这个名字是什么意思”“为什么要多这一步”“为什么放在基类”时，先用实际调用方
回答：业务对象是什么、操作前后发生什么变化、谁应该负责。若需要追踪多层实现才能解释，
检查是否存在职责错位、隐含模式或重复概念；不要只换一个英文近义词就结束分析。
解释时先给当前方法的直接用途、真实调用链和一个具体事件例子，再指出能删什么。
例如用“A 已发出取消，B 等待容量时超时”说明谁继续清理、谁仍占资源；不要只说
“原子发布”“状态有效性”“所有权转移”，也不要用大段术语替代对应代码。

- **名称从业务含义推出。** 先判断对象是角色选择结果、完整路由、交付输入还是资源记录，
  再选择名称。`Placement` 换成 `Attempt` 或 `Operation` 并不能自动变清晰；
  `Selection` 与 `SelectionResult` 也不能仅凭词尾判断是否需要两个类型。
  看两者的字段、生命周期和调用方是否表达不同事实，避免同义包装。通用名称仍须表达具体用途。
- **归属看表达的概念，不看谁恰好使用它。** 查清对象由谁创建、谁决定其内容、谁消费、
  是否持有资源。例如交付选出的请求及预测值适合由 `Delivery.Selection` 表达，
  Endpoint 消费它并不意味着它应成为 Endpoint 的内部类型；端点的请求和批次资源记录
  则由 Endpoint 管理。迁移类型时保留输入校验、精确身份和防御性复制，避免访问器引入重复复制。
- **基类只承载共同契约。** Direct 专属路径放在 Direct 实现，Queue 专属路径放在 Queue
  实现；纯抢占动作由抢占组件负责。方法能访问基类字段、多个地方调用，均不足以证明应该上提。
  先区分共享的状态操作与特定策略，再决定复用位置，避免用基类串起所有模式。
  取消入口负责本请求的取消和资源处理；抢占等其他流程依据自身请求和实际资源变化推进，
  不要求每条取消、结束路径手工续接另一套协议。共用清理与通知仍须保留实际责任交接。
- **区分调用执行与回报结果。** 画出一条真实调用链，标明谁做决定、谁提交变化、谁执行、
  谁消费结果。Scheduler 委托交付组件后，交付组件不应再调用 Scheduler 完成同一提交；
  它可以报告交付结果，由 Scheduler 决定重试或结束。同步返回的结果直接由调用者处理，
  不为统一回调形式额外绕行。异步结果反馈本身不等于错误的循环依赖。
  状态所属对象接收所需输入、完成自身变化并返回结果，不反向修改调用者的流程标志。
  允许独立执行的有效前缀与其他成员的失败通知分别确定责任，避免无关失败回调阻止已具备条件的工作；
  业务要求整体提交时仍保留整体约束。
- **状态决定动作，存储负责查找。** 类似取消操作，先取得对应请求，再依据其状态处理；
  不让业务调用方反复拼接 active/closed 等存储分区查询。统一查询仍须保留请求阶段、
  batch、代际和所属调度器的匹配规则，不能让旧请求操作命中新请求。
- **把隐含状态机说清楚。** 对事件处理函数，明确请求有哪些状态、每种事件允许哪些转换、
  每次转换有哪些动作及结束条件，再决定方法名和分层。若两个入口只靠传 `null` 区分正常
  调度与抢占等不同业务，应提供能读懂的入口或参数；不为形式统一隐藏操作目的，也不因此
  机械引入状态机框架。
  对每个状态写清谁读、谁写、什么事件设置或清除；不能用“领取任务后置 false”代替对并发
  通知的处理。多个标志确实互斥时优先用枚举；能同时成立的事实不能强行合并成互斥状态。
- **流程位置由时机契约决定。** 某一步需要“选出后立即交付”还是“等待队列条件满足”，
  要沿真实调用确认，不能因为共用辅助方法就塞进同一个阶段。角色差异、调度模式和交付模式
  分别核对；用户明确暂缓的流程调整不夹带到当前职责迁移中。
- **组件内部收敛流程，调用方表达目的。** 优先复用已有业务入口，不先新增另一套包装。
  线程安排、重复执行保护、完成通知和失败传播由执行组件负责；调用方取得完成结果后按需
  等待或接续工作，不分别组合执行器、回调注册和专用等待接口。跨多个对象确需“全部停用后
  才开始清理”时保留两阶段，先核对持有旧引用的接纳入口是否受全局关闭状态约束，不能
  仅凭目录已清空就删除屏障，也不把注册表和缓存等调用方职责全部搬进 Endpoint。
- **严格限制最小可见性。** 本类实现用 `private`，同包协作用包级，必要的子类扩展点才用
  `protected`，真实跨包业务调用才用 `public`。收敛接口时同步检查旧重载、同步便捷入口和
  任意 `Runnable` 执行入口；不为 UT 打桩或等待方便扩大生产接口可见性。具体审核与整理顺序见
  [先收紧可见性，再整理成员](#先收紧可见性再整理成员)。

## 用当前事实和正向条件写代码

- **变量名描述此刻保存的内容。** 尚未筛选的集合不能提前叫 `unmanagedRequests`；
  过滤前叫 `requestCandidates`，只有确认不再由 Scheduler 管理的结果才叫
  `unmanagedRequests`。检查名称在赋值、筛选和消费各阶段是否都成立，不能只符合最终结果。
- **主路径优先表达“满足什么条件，就做什么”。** 将连续的否定条件加 `continue` 整理为
  `registrationUnchanged && observationExpired` 等相邻、可读的正向判断；不要只给反向
  过滤换一个正向变量名。选择待处理对象时，优先直观表达保留条件，而非让读者从
  `removeIf(retainPredicate)` 的双重语义反推剩下什么。简单入口保护仍可早返回，
  不为消灭所有 `!` 增加深层嵌套、额外集合或无意义辅助函数。
- **让遍历和修改对象清楚可见。** `keySet().removeIf(...)` 修改的是原 Map，而不是独立的
  key 集合；涉及这种视图副作用时，代码要能直接看出修改的是候选快照还是实际请求账本。
  锁外筛选与锁内提交分开时，保留精确登记、阶段及最近上报时间的复查，不能因简化条件删掉。
- **清理条件、资源效果和返回统计分别命名。** `confirmed` 只表达 Worker 已确认执行事实，
  不等于请求完成；删除本地关联不自动等于释放 Worker 容量。TTL 的时间基准、受影响的
  请求类别，以及返回值是否只统计未确认预留，都应在附近代码中直接看清。变量如
  `removedAnyRequest`、`expiredUnconfirmedReservations` 应准确描述效果，避免只叫 `changed`、
  `count`。用户只要求可读性修改时保留现有契约，语义疑问单独指出，不夹带清理策略变化。

## 逐项追问：这个方法、这个成员可以删掉吗

在授权的审核范围内逐类检查，包括调用方与测试夹具；用户要求全量检查时，不只看最近
修改的几个大类。引用扫描用于找候选，逐项核对用途后才删除，不把扫描数量当作语义审核完成。

- **方法：** 谁在生产路径调用？是否只是多余重载、转调、旧模式入口，或仅 UT 使用的
  便捷接口？返回值是否真的改变调用方决策？先检查方法引用、反射、框架回调、序列化和
  自定义扩展契约；没有普通调用不等于无用。确认仅为 UT 服务的接口应移除，测试优先改走
  真实生产入口，必要的测试准备放在测试侧，不为维持旧测试新增生产兼容入口。
- **成员：** 谁写、谁读、何时清除？是否只写不读、只被 UT 断言、重复持有已有依赖，
  或可从已有可靠事实推导？同时检查维护它所需的数组、计数、回调及清理分支，避免只删 getter。
  缓存和索引需确认性能价值；不同生命周期的集合不能因内容相似就合并。
- **校验：** 参数所属对象在入口负责检查，接纳状态、精确身份和容量在实际提交变化处检查。
  同时核对 `Objects.requireNonNull`、`checkState`、`checkArgument` 及等价条件，不只清理一种写法。
  同一次持锁调用的包装层不重复下层已有校验；跨登记、入队、交付阶段的取消或下线复查仍须保留。
  具体删除判据按 [方法与校验职责](../evidence-first-implementation/SKILL.md#5-让方法和接口表达完整语义) 执行。
- **收益：** 清理目标是减少事实来源、交接步骤和理解成本。搬迁、改名或增加包装不算消除复杂度。
  对照本轮开始时的工作区统计生产、测试、文档净变化，排除其他并行改动；若整体精简却净增，
  逐段列出新增代码与用途，继续检查残留协议，而不是只解释“新增了输入和结果类型”。
  不能只用测试通过说明精简完成，也不能通过压行、搬进内部类或削弱契约制造减少的数字。

## 由 AI 理解流程，再组织代码

创建或修改任何具名类（包括有独立职责的内部类）时，先判断是否需要类说明，再改成员或实现。
这也适用于旧类和仅调整成员顺序的修改，不限于新增类或实质重构：

1. 旧类先读实现和调用方，为需要说明的类补齐缺失注释，修正已经过时或过长的说明；
   原说明准确且简洁时保留，不为走流程重写。
2. 新流程类先写清职责和预期主流程，再实现。类说明只概括本类负责的业务，不代替设计材料。
3. 依据确认后的流程组织成员并实施本次修改，完成后再核对说明与代码一致。
   发现旧注释和实现矛盾时先查明实际契约，不能为迎合注释擅自改变现有行为。

流程类通过实现和调用方确认以下问题，但不要将这份检查清单全部抄进类注释：

- 类负责的业务对象及边界，哪些独立入口会触发它。
- 从进入、处理、等待到结束的主要步骤；在哪个线程执行，哪里会异步交接。
- 关键状态代表什么，谁修改，何时失效；失败和取消后谁继续清理。
- `start`、`stop`、`close` 的真实效果：启动什么、停止接纳还是停止执行、是否等待、
  最终释放哪些资源。不能只看名字假设生命周期。

类 Javadoc 默认只写 1–3 句话，通常是职责、主流程、一个确有必要的关键边界。
使用简洁的多行格式；不要罗列全部方法、字段、状态、异常分支或调用链，不逐行翻译实现，
也不堆叠“本类不负责什么”。命名和字段已自解释、没有自定义行为的简单 record、DTO 和枚举
可以没有类注释，不为了满足形式重复代码。有单位、特殊取值、身份约束、校验、资源或生命周期
语义时需要说明；局部约束优先放在相应字段或方法旁。不为数据类编造启动、停止流程。
有必要的局部细节放在对应代码附近，避免类注释盖过主体逻辑。
流程变化时同步修改说明；本次未涉及的类不顺手批量添加模板注释。

例如，只有在实现确实满足时才这样说明：

```java
/**
 * 执行请求任务：接收并处理请求，停止接收后等待已有工作结束，再释放执行资源。
 * 用户响应回调在请求锁外执行。
 */
```

### 先收紧可见性，再整理成员

- 逐类核对字段、构造器、方法和内部类型的实际使用范围，包括 Lombok 生成的访问器。
  先确定哪些成员需要对外暴露，再按最终可见性组织代码；不能只运行排序或格式工具，
  就宣称完成了作用域审核。
- 状态和依赖字段默认保持 `private`。基类字段不能因为子类存在就统一声明为 `protected`；
  仅保留真实子类需要的依赖和扩展点，不提供只为读取内部字段而增加的公开 getter。
- 引用扫描用于定位候选，随后核对方法引用、反射、Spring 装配与回调、JSON 序列化及跨模块
  扩展契约。没有普通 Java 调用，不足以判定一个框架入口可以收紧；也不为假设中的未来调用
  保留不必要的公开入口。
- 测试优先通过真实业务入口验证行为。确需准备内部状态或复用依赖时，使用测试侧已有装配对象、
  夹具或必要的反射，不反过来扩大生产成员的可见性；反射准备不能替代对真实业务调用的验证。
- 可见性调整后重新整理成员顺序和注释归属，保持初始化顺序及 Lombok 构造器参数顺序。
  编译整个 Maven reactor 的生产代码和测试代码以检查调用方，再按风险运行相关测试，
  最后通过全仓成员顺序和 Spotless 检查；保留用户要求保留的红测，不为通过验证放宽断言。
- 交付时区分“已检查且无需调整”和“实际移动或收紧了成员”，说明保留的框架入口、跨包接口
  和扩展点依据，不把编译或脚本检查通过当作所有成员均已具备最小可见性的证明。

### 成员顺序与人类阅读顺序

- 字段及初始化块在前，构造器随后，方法按
  `public → protected → 包级 → private` 分组，内部类型放在方法之后并递归整理。
- 各可见性组内，按类的真实流程放置业务入口及相关方法。多个独立入口的顺序由 AI
  结合类流程说明判断，不能用字母顺序、方法长度或调用次数代替业务判断。
- 字段优先呈现常量、核心依赖与配置，再呈现运行状态、索引与缓存、诊断信息；
  相关成员成组留白。但同类初始化操作的相对顺序、实例字段顺序和 Lombok
  构造器参数顺序必须保持。受到这些约束时用空行或简短分组说明改善阅读。
- 方法名、变量名直接说明保存的数据或实际动作。避免用模糊的 ownership、terminal、
  settlement 等词统称不同职责；已有领域术语需要准确指向具体对象或行为。
- 将用户已确认的流程顺序作为修改依据；不要让自动排序反复打乱人工安排。

### 排序脚本的真实边界

使用前检查仓库内 `tools/order_java_members.py --help` 和实现，避免依赖过期能力描述。
现有版本按成员类型、可见性和源码调用关系排序；不理解业务重要性，也不解析自然语言
流程或 `MemberOrder` 声明。类注释由 AI 理解后写，当前不能声称脚本会按该注释排序。

若要让脚本执行类注释中的流程，需在用户授权的工具改动范围内实现明确的声明格式、
方法签名匹配、缺失或歧义诊断和测试；不能仅写入注释就宣称能力完成。
排序前先预览影响范围，特别检查重载、回调、递归调用与多个独立入口。

## 功能与并发修改

- 一个状态表达一件事。引擎正在执行、占用本地容量、已收到完成反馈、Future 已完成、
  请求已清理归档是不同事实；不能以其中之一替代其他事实。
- 保留请求、一次尝试、Endpoint generation 和资源句柄的准确身份约束。
  旧回调不能修改新尝试，释放操作不能指向被替换的资源记录。
- 明确每次资源获取、物理发布、执行器接纳和清理的责任交接点。
  提交成功不等于发送成功，取消发出不等于资源释放，完成响应不等于全部清理结束。
- 释放入口由资源记录推导实际扣减项，避免让上游选择多种等价清理方法或传入“是否记账、
  是否通知”等可推导开关。调用方仍须提供真实的释放依据；资源记录无法自行知道的远端
  取消结果不能靠猜测。确认释放后及时更新有效容量，重复调用和旧上报不能重复扣减或恢复占用。
- 通知只负责唤醒和促使重新判断，不隐含修改资源、推进业务版本或再次清理。
  资源与失效版本在实际状态修改处更新，通知在锁外发出；检查同一次变化是否被多层重复通知，
  并验证变化发生在等待登记之前时不会丢失唤醒。
- 等待请求的结束与已交接取消的请求分别收尾。若没有为等待者专门预留容量的契约，
  不额外维护二者的抢占绑定、专属监听和提交协议；被取消请求通过普通完成或取消确认释放资源，
  触发正常调度。等待者超时不撤回已发出的取消，也不提前释放对方资源。
- 不在请求锁内执行用户回调、网络等待或昂贵计算。涉及锁覆盖与交接时，
  沿真实路径核对锁顺序、异常分支和回调重入，不能仅凭“有锁”宣称安全。
- 执行器负责它实际接纳的任务。优先复用标准执行器、Future、现有队列及线程归属，
  避免再手工维护一套重复的全局任务计数或集合。确有必要新增跟踪时先解释其覆盖的
  独有事实，以及登记、交接、拒绝、合并和释放如何集中管理。
- 队列为空、线程处于 WAITING 或某个瞬间 activeCount 为零，都不能独立证明清理结束。
  关闭方案必须覆盖同步调用方、已接纳工作、后续任务和晚到回调；关闭执行器前确认
  谁还会提交任务。不能用固定睡眠、过早 shutdown 或忽略拒绝来掩盖交接问题。
- 保持当前契约中的策略选择、等待条件、重试预算及超时语义。标准机制不能直接替换时，
  解释具体阻碍；不能为删除计数或减少类数偷偷改变业务行为。
- 容量通知只表示应重新检查，不表示取消已完成或容量已转交给抢占发起者。审核抢占要沿
  “取消、实际释放、通知、竞争接纳、原请求重试”走完整链路，检查释放是否过早、其他请求
  是否可能取得容量，以及原请求是否因持续拿不到容量而重复取消其他请求。
- 同步清理被替代的入口、包装、字段和测试夹具；不保留两套互相竞争的状态来源。

## 从业务事实简化实现

解释、审核和重构时，先回答“这段代码处理什么事实、哪些结果必须一致”，再判断当前
锁、类、字段和缓存是否必要。职责有必要，不代表承载它的现有类和实现方式有必要。
结合具体代码说明依据，不用通用设计模式替代对实际实现的检查。

### 先核实数据契约，再选择遍历和匹配方式

- 沿生产入口追踪协议转换、Map 构造和写入，确认 key、对象身份、重复记录的处理规则。
  测试可以证明某种输入被覆盖，不能单凭测试人为构造的 key 推断生产协议。
- 先说明操作需要交集、差集还是完整统计。例如完成反馈需要匹配本地当前请求；
  活跃反馈还可能需要统计本地未知的占用，不能统一改成只处理交集。
- 两侧使用相同 key 且查找成本合适时，优先遍历较小集合查另一侧，避免额外构造交集
  或索引。ID 匹配后仍核对请求阶段、batch 和代际等实际身份条件。
- 请求状态与 batch 汇总分开处理：更新请求记录时收集受影响的 batch，再逐个汇总其当前成员。
  不为同一批成员在准备、提交和预测阶段反复转换多份列表或维护平行状态表；批次的资源边界
  与执行结果仍由批次负责，不能因合并遍历丢失批次约束。
- 合并、去重和补偿分支必须有真实输入契约支撑。发现测试与生产转换不一致时，查清
  哪一方表达正确契约再调整，不为兼容人为测试输入增加生产复杂度，也不为过测试删掉真实约束。

### 按最小业务原子单元缩锁

- 分清锁内工作：读取可变事实、身份与条件校验、状态提交、排序与估算、通知与结果组装。
  优先减少重复扫描和中间结果，移出不依赖实时可变状态的计算；关注实际处理量，不只数代码行。
- `List.copyOf` 等通常只冻结集合成员，不能冻结成员对象的状态。区分防止遍历期间修改的
  集合副本与可在锁外计算的值快照，不因“已经 copy”就把状态读取和删除拆开。
- 先确认是否需要整轮原子性。清理可按独立请求或 batch 分段持锁时，候选只负责枚举，
  每个单元在同一次持锁中核对当前身份、最新时间和清理条件再删除；保留 batch 整体约束。
- 清理候选先过滤到可能需要处理的记录，不先复制全表、再查询外部、最后重扫全表。
  若只需在锁外按 ID 查询 Scheduler，可保存原记录引用，回锁后核对仍是同一记录并读取最新
  过期时间；不必复制阶段、时间再额外定义候选 DTO。引用不是状态快照，可变字段仍在锁内读；
  若判断确实依赖过去时刻的值，则保留必要的值快照。
- 不默认用“全量快照、锁外计算、版本不符整轮重试”解决长临界区。先考虑直接核对并提交
  当前事实、锁外构造派生结果。确需乐观校验时，说明无法采用简单路径的原因、版本覆盖的
  全部依赖及冲突成本；不能假定现有调度版本会覆盖每次时间基准或执行结果更新。
- 缩锁不能悄悄改变失败语义，例如从预测失败前不提交变成先提交再预测。

### 保留有用能力，重新判断类和成员是否必要

- 逐字段检查保存内容、来源、读取位置、可派生性及存活阶段。字段被使用，不足以证明
  必须单独保存；反过来，不为减少字段把必要信息变成隐含约定或锁外读取实时状态。
- 讨论是否保留一个类时，先检查已有接口和数据类型能否承担职责，再提出新增包装。
  优先让队列快照负责队列转换、工作量快照负责工作量计算；不要在外层重复实现已有缓存。
  但不能仅为减少类数，把同样的状态机和字段全部搬回 Endpoint。
- 缓存需要说清：缓存什么、避免哪项重复工作、何时失效、谁发布、并发读者如何复用、
  何时释放请求上下文引用。区分输入转换、工作量汇总与每个新请求的耗时估算，不能把
  “复用输入缓存”解释成“不再估算新请求”。未经测量不声称缓存收益或锁竞争改善已被证实。
  包含同一基础视图的汇总对象不自动需要另一套缓存；低频诊断、拒绝解释和统计优先考虑按需
  读取，避免独立的缓存写回、版本复查和失效维护。不要为了取消缓存把冷路径全表统计搬到
  每次正常选址。版本校验、预测缓存失效和队列计数各自表达用途，不混进含义模糊的 Progress。
- 首次计算、缓存命中、模型变化和状态版本变化用清楚的分支表达。避免嵌套三元表达式、
  多层 Stream/lambda 和只为缩短方法而增加的跳转；先改善职责和控制流，再交给格式工具排版。
  独立的纯状态转换用命名明确的静态函数和普通 `if`/`switch`；已有事件类型能准确表达语义时，
  不再定义同义枚举然后逐项转换。抽函数应隔离明确职责，不只是把难读表达式藏到另一个名字下。
- 名称使用已确认的业务术语；术语表未收录的词既不自动禁止，也不自动合理。需要反复
  解释的 `Projection`、`materialize` 等名称，应优先换成具体业务对象和动作。
  说明“同时修改两个类”时直接这样说，不用“同步快照”等容易被理解为运行时数据同步的表述。

## 验证与交付

按改动风险验证，使用当前模块配置中的真实类名和测试工具：

- 默认 `./mvnw test` 同时运行功能 UT 和性能回归，包括选路分配量测试及 Schedule RPC
  容量/模式/QPS 矩阵；不在默认配置中排除性能标签。专用 profile 只用于单独复验。
  性能阈值失败须如实记录，不跳过用例或放宽阈值换取通过。

- 行为或生命周期重构先运行现有 UT 固定基线，补齐缺失契约后再改生产代码；模式与角色
  分支要覆盖实际支持的组合，尤其不能遗漏 encoder。纯死代码删除不机械新增镜像测试。
- 用户确认的跨组件约束要转成可执行验证。先补 UT，确认旧实现因预期的约束被违反而失败，
  再改实现；不要把编译错误当作契约测试的有效失败。职责边界可用架构测试限制禁止的调用，
  原子性用锁存器或屏障验证校验、许可转交和状态记录之间不能插入取消，结果测试验证回调在
  锁外且执行组件没有自行决定重试或结束。按实际风险选择，不为普通类型搬迁复制整套测试。
  迁移后同步清理旧入口和测试夹具；测试通过之外，还要重新阅读完整链路判断是否更清晰。
- 测试失败先区分用例契约不对、重构回归、原有失败和环境干扰，用改动前后相同用例或
  隔离复现给出证据，不直接修改预期让测试变绿。共享工作区并发构建污染产物时，用独立副本
  验证并带齐跨目录测试数据；报告完整运行与分次补验的区别，不把历史结果当作当前验证。
  Mock 绕过构造器制造了生产中不可能存在的对象时，改用合法的错误身份或过期对象验证原契约，
  保留资源余额、状态和异常等业务断言，不为无效夹具恢复生产冗余分支。
  并行工作区仍在变化时限定自己的差异；不要为追求全绿持续接手无关编译错误或全仓格式修改，
  应报告阻碍、归属和已验证范围，不把他人的增删并入自己的成果。
- 用户要求“先加红测”时，只补测试并确认失败来自指定行为，保留红测，不顺手修生产逻辑。
  容量用例优先使用真实 Endpoint 账本，覆盖请求数、硬 KV、预估 KV 边界、拒绝无副作用、
  重复及旧身份释放、Worker 上报校准、锁外通知和抢占后的竞争；不靠 mock 预设容量已释放。
- 用户明确说明有其他 agent 并行修改、无需追求 UT 通过时，停止反复全量构建和修复无关
  失败，完成本次引用、可见性及局部校验并如实报告限制。若随后明确要求确认红测，可针对
  该用例运行；不能把这种阶段性验证安排永久推广为项目免测规则。

- 提交 FlexLB 改动前必须执行并通过仓库的 pre-commit；不能用单独运行格式脚本代替。
  从仓库根目录运行 `python3 -m pre_commit run --hook-stage pre-commit`，检查本次暂存内容。
  每个 checkout 首次使用时安装 pre-commit 并设置 `git config --local core.hooksPath .githooks`，
  让普通 `git commit` 自动执行相同检查。不得用 `--no-verify`、`SKIP` 或停用钩子绕过失败。
- FlexLB Java 钩子检查输入文件的成员顺序及本次新增、修改类的 Javadoc 是否存在、
  有用途或流程摘要并采用多行格式。无自定义行为的简单 record、纯字段 DTO 和简单枚举
  免于强制类注释；结构简单不保证语义自解释，隐含约束仍须审核。未触及的旧类不追溯补齐。Spotless 对整个
  Maven reactor 做只读校验。钩子在隔离的 Python 环境安装解析器，不依赖个人目录。
- 类说明是否准确、是否简短、是否覆盖真实流程仍须 AI 和人工审核；不能声称
  pre-commit 可以理解业务语义或完全阻止绕过本地 Git 钩子的提交。

- 命名、注释、排序等低风险修改不机械新增行为测试。成员移动应核对方法体、注解、
  注释归属、初始化操作和 Lombok 参数顺序；语法树检查不等于完整行为等价证明。
- 审核本次触及的类是否已有准确、简短的类说明，成员组织是否对应说明中的流程；
  删除复述实现或与其他说明重复的长段文字，不能以增加注释行数代替可读性改善。
- 并发或清理修改覆盖接纳与关闭竞争、后续工作交接、提交拒绝、重复通知、取消、
  晚到回调和部分失败。优先用锁存器或屏障构造交错，不靠随机等待碰运气。
- 从 `rtp_llm/flexlb` 使用 Maven Wrapper。针对受影响模块和测试执行验证，例如：

  ```bash
  ./mvnw -pl flexlb-balance -am test -Dtest=<实际测试类> -Dsurefire.failIfNoSpecifiedTests=false
  ./mvnw spotless:check -Pspotless-check
  ```

- 代码修改完成前按仓库要求运行整个 Maven reactor 的 Spotless 检查，不能拿模块检查
  冒充全量通过。成员排序还应运行脚本的检查模式；改脚本时运行其真实回归测试。
  脚本依赖和命令以仓库 README、requirements 和 `--help` 为准。
- 格式化只处理授权范围，遵守当前会话的文本补丁工具要求。全量检查遇到无关改动时，
  查明原因并如实报告，不为让检查变绿覆盖用户工作或无边界扩展格式化范围。
- 架构或行为改变时更新相关现有架构说明；局部改名和排版不新建大篇设计材料。
- 用户要求单独提交纯格式改动时，不能整文件暂存夹带已有功能改动。必要时在隔离工作树
  基于提交基线重现格式转换，审核实际提交树，再保留原工作区的功能修改。
  不未经授权改写历史、清空暂存区、推送或创建额外提交。
- 交付说明具体改动、执行过的验证、失败或未完成项。将“读过源码”“测试通过”与
  “真实环境验证”分开；不要把脚本能力、设计方案或局部测试描述成已经全面落地。
