## 迟到 completion：一个实例，保留原始失败

新增 `late_completion::after_missing::single-batch`，配置在
`scenarios/status/late_completion.yaml`。YAML 声明拓扑与参数，Python 程序负责步骤，
`scenario/actions/late_completion.py` 负责注入和取证。

这是**异常上报下的 Master 健壮性测试**。正常真实引擎和正常 mock 的完成快照是原子的；
不能把这条用例解释为普通执行变慢必然造成状态空窗。

1. 在 1P/1D 环境发出一个真实 BATCH 请求，暂不 Fetch。通过既有
   `/rtp_llm/inflight_status` 确认 Master 已持有唯一 Decode confirmed owner。
2. 记录目标引擎的正常 running 响应，然后将该 rid 从一个实际状态响应的 running、finished
   两张名单同时隐藏。内部执行状态保持原样。
3. 等待业务接口的 confirmed 计数归零，并记录后续恢复的 running 响应，排除引擎死亡、RPC
   永久无响应等其他原因。这里不以固定 sleep 代替确认，也不增加 Master debug 接口或日志。
4. 客户端 Fetch 触发正常后续执行。真实成功 completion 延迟发布；确认其使用新版本交付，
   且 Master 后续请求的游标已确认该版本。
5. 在完整 30 秒业务窗口内检查 scheduler_inflight。归零为 PASS；保留 1 为原始 FAIL。
   缺少前置证据、请求失败或构造错误为 ERROR，不能算作缺陷复现。

`late-completion.json` 保存业务样本、客户端终态和目标引擎的 **post-filter** 响应。
`worker_status_delivery_fault` 包含引擎、端口、epoch、状态版本、请求游标、发布版本与目标记录。
这些证据与 `DecodeEndpoint.doCalibrate` 的分支共同支持 settled 丢弃的归因；没有声称直接
记录到了该分支的执行日志。用例不配置 finding/xfail 包装，FR-3 修复前会使回归红灯。

两个注入通过现有 `/inject` 接口使用：

| type | 参数 | 行为 |
|---|---|---|
| `status_missing_rounds` | `rid`、`rounds` | 在 N 个成功状态响应里隐藏目标的 running 与 finished；无响应 RPC 不消耗轮数 |
| `status_completion_delay` | `rid`、`delay_ms` | 保存真实终态，到期且缺席轮数耗尽后，在下一次正常状态请求中发布 |

延迟记录在发布时才获得 completion version；等待期间不提前推进游标。`clear_inject`
会立即发布积压记录再解除注入；关闭 delay 会在下一次状态请求发布积压记录；crash 丢弃进程内
注入状态。故障关闭时保留原先的锁、完成顺序和容量裁剪语义。参数限制只约束测试注入接口。

## 重复运行门禁

`completion_race_gate.py` 重复现有 `balance_distribution::length_mixed::batch-window`。
每轮独立环境，只读取运行结束后的产物，不加入在线观测。并行度由 `--lanes` 控制，
每个 lane 的 Master、mock 端口窗口独立，运行计划必须完全落在申请的端口块内。

在已申请的远端租约环境、`online_eval` 目录执行，例如：

```bash
python3 completion_race_gate.py --rounds 20 --lanes 1 \
  --port-base "$FLEXLB_PORT_BASE" --port-block 1200 \
  --out-dir "$FLEXLB_RUN_DIR/completion-gate"
```

`--port-block` 必须填本次实际租约大小。4 lanes 至少需要 900 个连续端口；单 lane 至少 300。
脚本对 `result.json`、cleanup、五个 clean 阶段及采样完整性逐项核验。超时的 action 来不及返回
artifact 列表，但 finally 已保存采样；脚本按阶段时间范围匹配唯一文件，缺失或歧义均视为无效。

- `PASS`：完整执行通过，最后 scheduler 计数为零。
- `ZOMBIE`：30 秒 clean 超时且覆盖整个窗口的采样持续非零。
- `INVALID`：环境失败、其他阶段异常、缺失/矛盾证据或不完整执行。

`summary.json` 与退出码一致：0 全部通过，1 至少一次 ZOMBIE，2 存在 INVALID。
离线复核可用 `--analyze-dir <原始门禁目录> --out-dir <新目录>`，不会改写原始结果。
每轮只有 40 个请求，不能把它宣称为 completion 容量 1000 的极端裁剪覆盖测试。

## 取消与完成的终态计数

FR-9 采用现有 `MockEngineCancelChannelTest` 的 Java 单测方案。原有请求结束日志不能代表
Master 实际可收到的完整 `WorkerStatus` 终态集，因此直接检查引擎保留的记录：

- 完成先发生：P 和 D 各一条成功记录；随后 Cancel 返回 NOT_FOUND。
- 取消先发生：P 一条 typed 8429 CANCELED，D 一条普通 CANCELLED；等待 P 批次回调退出后
  再核验完整集合，不能只过滤并数取消记录。
- P 已完成、D 仍执行时取消：P 的执行成功和后续优先级控制终态是两个阶段；D 只有一个执行终态。

统计按引擎/epoch/rid/batch 和控制阶段区分。相同游标重复读取的同一记录不重复计数，
已确认游标不再返回该记录。没有修改 mock 的取消逻辑，也没有新增 YAML 实例。

## order_basic

占位请求执行 3 秒时，后续六个 peer 全部排队，因此期望为
`70a → 70b → 50a → 50b → 30a → 30b`。程序明确传入 `first_peer_exempt: false`，
PR1 打分集合同步包含全部 peer。参数为 true 或缺省时仍保留原有首 peer 豁免语义。
占位、pending、slow 步骤及相邻 FIFO/normalize 断言保持原样。
