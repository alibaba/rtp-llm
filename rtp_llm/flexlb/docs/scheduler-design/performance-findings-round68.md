# FlexLB 性能瓶颈：第 71–76 轮结合层次重构的进展

## 范围

第 53–70 轮在第 52 轮冻结版本上分析瓶颈。用户授权结合其他 agent 的层次重构继续后，
第 71 轮重新冻结当前源码并实现提交快照优化；第 72 轮集成 RequestScheduler 接口拆分，第 75–76 轮验证两个完整调度器实现及最终排空边界。

原 Master P99 <50ms 门槛尚未稳定通过。以下历史分析须与新版本测量区分。

## 两个被实验否定的简单推断

1. **“把 payload 压小就能解决延迟”**：保持 token 数量、将编码字节减少 66%，
   吞吐仅增加约 10%，P99 仍 574–692ms。真实 token 值当然不能这样替换；这只是诊断。
2. **“提前解析能普遍降低 P99”**：固定计划 10K QPS、32 规划线程、8 额度，
   原流程 P99 88/107ms，提前解析 129/107ms，没有稳定改善。

## 当前最需要控制的测量变量

原 burst 发压没有固定到达曲线，实测 offered QPS 可从 10.68k 波动到 13.31k。
固定计划 10K QPS 后，平均实际速率一致，但仍有 18–32ms 平均发压迟滞，会形成追赶突发。
发压器、Master、Mock 共用 JVM，GC/JIT/调度的影响尚未分离。

第 69 轮已记录三次各 8192 条请求时间线：Master P99 为 118/64/63ms，客户端 P99
却为 153/159/168ms。全局等待是服务端提交前长尾主体；发压器迟滞也不可忽略。
详见 [到达、排队与 GC 时间线图](performance-flow-round69.png)。

另已确认“规划名额”计算完成后不会释放，要等串行提交的 finally 才释放。
因此它同时覆盖计算和已完成结果的等待，不能当作纯计算线程容量。
第 70 轮已补齐真实名额释放：完整持有时间的 79%–81% 在等待提交，规划占 15%–17%。
8192 次串行提交累计墙钟 388–445ms，同线程 CPU 194–211ms；三处 Prefill/Decode
锁等待占提交墙钟 34%–40%。GC 与最长提交明显重叠，这些数值不能作为互斥阶段相加。
三次 Master P99 为 114/80/117ms。优先继续分析串行提交的 Prefill 共享锁和突发恢复，
并将发压移至独立进程以分离共同 JVM 暂停；现有证据不支持直接加规划线程或提前释放名额。
原 burst 性能回归和 50ms 门槛保留，诊断负载不能替代它。

## 提前解析原型的 review 结论

67 项定向回归通过，三个独立 review 完成；正常单次初始化路径未发现身份/重试阻断。
原型仍有公开 setter 并发替换的双字段中间态、getter 不再保证原始字节、follower 提前
做无用解析、异步回调仍持有整份原始请求等边界。因此原型已撤销，未投产。
JVM 窗口分配减少不能证明存活内存减少；Context 也不应因该实验承担解析执行职责。
