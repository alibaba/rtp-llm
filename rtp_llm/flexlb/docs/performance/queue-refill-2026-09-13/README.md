基线：`addd5cee6b`；修改后：`54dd6e5763`（包含 `7c4e72e7aa` 的容量快照修复）。

**UT 通过。两轮性能对比未证明稳定提升；BATCH 10000 QPS 仍未达标。**

## 改了什么

协调器仍然是一个协调线程加固定大小的选路线程池。线程池名额只限制同时进行的选路，
不代表 endpoint 数量或机器容量；机器增删仍通过现有路由快照、准入校验和容量事件处理。

旧循环只有两种互斥动作：有结果就提交一个结果，没有结果才补充选路任务。
因此，R1 提交完成释放名额后，只要 R2 的结果还在队列里，R3 就不能使用空出的名额。

新循环固定做三件事：

1. 有完成结果就处理一个。
2. 按 FIFO/优先级把空出的名额分给待选路请求。
3. 在锁内重新检查：既没有完成结果，也不能继续选路时，才等待事件。

R1 完成后，R3 可以立即开始选路，与协调线程处理 R2 的准入重叠。
选路和准入仍在协调锁外，`Condition.await()` 会释放锁。
这个改动消除了结果积压导致的选路线程空闲，但协调线程仍串行处理准入；单个准入很慢时，
后续准入仍会等待。容量等待、取消、关闭和端点派发沿用现有流程。

完整 UT 期间还发现容量投影缓存的竞态。快照在锁内读取、锁外生成，原实现只把缓存置空；
正在生成的旧快照可能随后写回，将缓存失效覆盖。现在容量阻塞/唤醒递增已有的调度输入版本，
晚到快照即使写回也无法命中新版本。这个独立修复放在 `7c4e72e7aa`。

## 结论和限制

**完整 UT 通过；这两轮没有证明端到端性能稳定提升，BATCH 性能验收仍未完成。**

- BATCH 10000：第一轮吞吐 5745.3 → 6162.7（+7.3%），第二轮 6343.7 → 6126.6（−3.4%）。
  新版两次均低于 9800 QPS 门槛，P99 为 6746.764 / 8546.948ms，均严重超过 250ms。
- BATCH 3000：新版吞吐两次均约 2997 QPS，但 client P99 分别为 354.564 / 173.375ms，
  一次失败、一次通过。旧版第二轮也通过，因此不能把首轮旧版的严重积压全部当作新版收益。
- NON_BATCH：前后两档均通过。10000 档吞吐第一轮略降，第二轮基本持平；
  3000 档首轮 P99 差异很大、第二轮都在几毫秒以内，没有足够证据宣称稳定的大幅提速。
- 单元测试证明了两个具体问题得到修复：积压结果不再延迟补充选路任务，过时容量快照不再重新命中缓存。
  这不等于它们是 750P/750D 端到端吞吐的主瓶颈。
- 这是包含两项修复的整体比较，没有做单项消融，不能把某个吞吐变化单独归因于主循环。
- 在 15 逻辑 CPU、48 GiB 内存的开发机上串行运行；采样未发现其他 Maven 压测，
  但桌面、IDE 和系统进程仍在运行，机器并非独占环境。两轮足以揭示本次结论不稳定，
  不足以给出普遍适用的性能增益。
- 10K BATCH 的 `route_submit_p99` 仍达到秒级；该指标是阶段延迟，不能据此直接判定 CPU 热点。
  本轮未新增 profiler 采样，不把历史采样结果当作这次改动的因果证明。
