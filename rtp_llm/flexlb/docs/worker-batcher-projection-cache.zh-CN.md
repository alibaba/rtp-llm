# WorkerBatcher：调度输入版本与快照缓存

`schedulingInputVersion` 表示队列之外的调度输入发生了变化：worker 状态、预测输入，
或者派发容量的阻塞/恢复。它让正在等待的调度决策重新检查输入，也使基于旧输入的路由快照失效。

## 写入规则

版本号是 `volatile long`。全部写入只发生在 `schedulingInputsChangedUnderLock()`，
该方法检查调用者是否持有 `queueLock`。锁保证递增互斥；`volatile` 保证锁外缓存检查能看到更新。
不再同时使用锁和 `AtomicLong` 来保护同一个递增操作。

| 事件 | 记录输入变化 | 唤醒派发线程 |
| --- | --- | --- |
| 队首进入/离开容量阻塞 | 是 | 此路径由派发线程自己执行，不额外唤醒 |
| 收到容量恢复通知且存在阻塞 | 是 | 是，重新检查容量条件 |
| worker 状态或预测输入变化通知 | 是 | 是，重新检查调度决策 |

记录变化的方法不隐含 `signal()`。是否唤醒由事件处理处明确决定。
容量通知仍只是重试条件，最终是否能派发由真实容量检查决定。

## 缓存规则

`ProjectionVersion` 把已有的三个版本组合成一个值：队列版本、调度输入版本、所有权版本。
没有增加新的版本计数器。版本是否仍然有效只由 `isCurrentProjection()` 判断。

`ProjectionSource` 把一次锁内读取的数据和对应版本放在一起，包含所有权快照、批量约束和容量阻塞状态。
这两个 record 是快照数据，不是独立服务、队列或可变状态管理器。

`captureRouteProjectionInputs()` 的流程为：

1. 锁外检查已有缓存，有效就直接返回。
2. 未命中则加锁，重新检查缓存；仍未命中才读取 `ProjectionSource`。
3. 解锁，排序并生成最终快照。
4. 加锁，在同一个临界区内检查版本并发布缓存。

缓存发布与队列版本、调度输入版本、所有权版本的更新使用同一把 `queueLock`。
旧快照可以返回给已经开始的读取，但不能在状态变化后重新成为有效缓存。
版本变化如果发生在发布之后，下一次读取会拒绝旧缓存。

没有把排序和 `work().materialize()` 移入锁内。已有缓存命中也不需要创建新的版本对象或获取队列锁。
未命中时增加两个小的快照数据对象，并在发布时重新获取一次锁；这部分代价需要测试，不能假定为零。
