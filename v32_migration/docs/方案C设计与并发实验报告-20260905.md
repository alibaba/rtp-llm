# DSA KV Offload 方案 C：设计与并发实验报告

日期：2026-09-05 ｜ 模型：DeepSeek-V3.2-Exp ｜ 硬件：2 × (8 × H20-3e 140.40GiB) 基线：`rym/feat/dsa_offload @ 5cb4bd891`，本目录所有改动未提交，`git status` 可见全部差异。历史背景和踩坑记录见同目录 `HANDOFF.md`（原封保留，未改动），本文只写当前生效的设计和 9/4–9/5 的并发实验。

## 1. 问题是什么

DSA sparse attention 的 indexer key 和主 KV 是两个 tensor，但共用同一张块表。offload 释放一个块，两者同时失效。而原生打分 kernel 假设所有 token 的 key 都在 GPU：块表被置 0 后它不会报错，而是去读物理块 0，安静地算错。这是整个项目最贵的一课——五个 bug 全是这种静默数据污染，没有一个抛过异常。

所以 offload 主 KV 的前提是：先让 indexer key 的完整性和主 KV 解耦。

## 2. 当前设计（方案 C）

一句话：indexer-K 独立成池全量常驻 GPU，主 KV 的历史部分放到 pinned host mirror，attention 选中谁就按 token 粒度取回谁。

### 2.1 indexer-K 独立 cache group

引擎层把 KV 预算切成两个池：`default`（主 MLA KV）和 `dsa_indexer_k`。offload 只释放 `default` 的块，indexer-K 永远完整地留在 GPU 上。打分 kernel 读到的始终是全量历史，offload 和非 offload 的请求走同一套计算，不需要任何特判。早期用 Python 影子池做的同一件事已废弃（见 HANDOFF §11），现在是引擎原生实现。

D 端每卡 12GiB KV 预算的实际切分：`default` 约 8.07GiB（1925 个可用块，每块 4.289MiB），`dsa_indexer_k` 约 3.93GiB。

### 2.2 pinned host mirror（V32AdmissionStore）

主 KV 的历史块保存在 pinned host memory。分配走 C++ 池复用，且在 P 端做 prefill 的同时异步执行——实测 admission 的阻塞等待只有 0.004ms，准备时间（约 1.8s）完全和 prefill 重叠，不进 TPOT。

生命周期用 block0 + generation 管理，30 秒墓地延迟释放防 fetch 线程 UAF。这是补丁式设计，能扛住已复现的顺序重用场景，但长期应该换成稳定 request_id + 显式 lease（见 §6 风险）。

### 2.3 token 粒度无损取回

先说被废弃的路：方案 B 的块粒度有损 warm pool（32 块 FIFO 缓存 + 异步预取，miss 即丢弃选择）。死因是算术不成立：每层 miss 散在约 200 个不同的块里，32 块的缓存命中率上限 16%、实测只有 2.0–2.6%；且为救一个 token 约 1152B 的有用 KV 要搬 73.7KB 整块，64 倍字节放大（判决过程见 HANDOFF §8.3）。缓存救不回来，因为 top-k 的访问模式本来就散。

C 的替代做法是不猜、不缓存：每步 attention 之前，窗外的选中 token 当场按 token 粒度从 host mirror 精确取回。两个 kernel 插在打分和 attention 之间，引擎块表和 attention kernel 都不改。

**先看块表**。每请求一张 `bt[]`（逻辑块号 → 物理块号），attention kernel 拿 token 位置 `t` 自己翻译：`物理行 = bt[t/64]*64 + t%64`。offload 后块表分三段（以 62,830-token 请求、982 逻辑块为例）：

```text
逻辑位置      bt[] 内容
─────────────────────────────────────────────
1..32        指向 32 个 staging 物理块（scratch 用）
33..725      0 哨兵（主 KV 已进 host mirror）
726..981     真实物理块（最后 256 块 = 16k 驻留窗）
```

中间那段就是危险区：attention 拿窗外 token 的位置直接翻译会得到 `bt[..]=0`，去读物理块 0——不报错，安静地算错。

**`lossless_mask_kernel`（重映射）**：逐个检查这层 top-2048 的选择。窗内的不动；窗外的按顺序分配一个 scratch 槽 k（0..2047，槽 k 物理上位于 staging 第 k/64 块的第 k%64 行），并把该选择改写成假位置：

```text
p = jpos[k/64] * 64 + k%64      （jpos[i] = staging 第 i 块在块表中的逻辑位置）
```

**`lossless_fetch_kernel`（取数）**：对每个分配了的槽，把该 token 这一层的 KV 行（约 1.15KB）从 pinned host mirror 经 PCIe 拷进槽里。它排在同一条计算流上，attention 天然等它完成，无需额外同步。

**走一个例子**：第 5 层 top-2048 里有窗外 token `t=20,000`（逻辑块 312，`bt[312]=0`）。mask kernel 分给它槽 k=137：k/64=2、k%64=9，staging 第 2 块在块表逻辑位置 `jpos[2]=3`，于是把选择从 `20000` 改写成 `p = 3*64+9 = 201`。fetch kernel 把 token 20,000 第 5 层的 KV 行拷到物理地址 `bt[3]*64+9`。attention 拿到 201，用原生公式翻译：`bt[201/64]*64 + 201%64 = bt[3]*64+9`——正好落在刚拷进来的槽上。窗内 token（如 `t=62,700`，逻辑块 979）不改写，走原物理块。

改写后的 201 是个假 token 位置，但 attention kernel 拿位置只做一件事：查表 gather KV 行。RoPE 等位置信息在 KV 写入时已烤进数值，token 20,000 的 KV 行搬到哪读出来都是 token 20,000 的内容。等价于借引擎自己的块表做了一次免费的间接寻址——这就是"不改块表、不加 hook"的含义。

**槽永远够用**：top-k 就是 2048，最坏全部窗外也恰好 2048 槽（32 块 × 64 行）一一对应，overflow 恒为 0。每层用完即弃、下层重新分配，32 个物理块按层复用——所以它是 scratch，不是缓存，方案 B 的"warm pool"概念在 C 里不存在（env 名 `STAGING_BLOCKS` 是历史遗留）。另一个常见混淆：历史讨论里的"warm pool 16k"是把两个东西记混了——16k token（=`KEEP_BLOCKS` 256 块）是驻留尾部窗，warm pool 从来只有 32 块。驻留窗挡掉约 94% 的 top-k 选择，剩下 ~6% 才走取回路径，这是整个设计经济性的前提。

GPU 侧驻留的只有：最后 256 块（16k token 尾部窗）+ staging 32 块 + 环 64 块。单测：取回 205 个 token，max err = 0，overflow = 0。

### 2.4 PD 分离下的双 group 传输

P 端按 tag 分别发布 `default` 和 `dsa_indexer_k`，D 端按 tag 分别恢复：indexer-K 和驻留窗内的 default 直接进 GPU；历史 default 经已注册 MR 的 GPU ring 中转后搬进 host mirror。RDMA 走内部 Barex，MR 注册要求 cudaMalloc backing（VMM 注册不了，`RTP_KV_POOL_BACKING` 强制）。

已知欠优化点：normal load 和 host load 目前是两次 cache-store round，协议上完全可以合成一个 tagged load plan，BlockTree 不用动。

## 3. 实验怎么做的

### 3.1 部署

| | P（11.17.131.204） | D（33.240.36.239） |
|---|---|---|
| 并行 | TP2 × DP4，EP8 | TP1 × DP8，EP8 |
| KV cache | 16GiB/卡 | 12GiB/卡 |
| runtime reserve | 8GiB/卡 | 8GiB/卡 |
| 每卡权重 | ~88.7GiB | ~99.9GiB（公共权重不切分） |

`max_seq_len=73728`，`seq_size_per_block=64`，`reuse_cache=0`，cuda graph 关，D 端 `concurrency_limit=32`。8 个 D rank 各有独立 HTTP 入口（27001 起，步长 9）。

### 3.2 Workload

固定 prompt（SHA256 `6f578b28...`），服务端 tokenize 后 62,830 输入 + 强制 8,192 输出（`min_new_tokens=max_new_tokens=8192`，top_k=1，seed 1234），总长 71,022，不碰 max_seq_len。`reuse_cache=0` 保证相同 prompt 不会共享前缀减压。

输出必须开到 8192 是有原因的：2048 输出时单 rank 能准入 5 条，但长输出的 KV 增长会让第五条在总长约 69,889 token 处把 default 池打满（1925/1925），增量申请失败。长输出下的稳定边界是 4 条/rank，这才是 32 = 4 × 8 的来历。

### 3.3 发压方式

`ThreadPoolExecutor` 每 20 秒提交一条非流式 HTTP POST，全部发给 P，由 `role_addrs` 显式指定 D rank（`ports[index % 8]`，每 rank 精确 N 条）。单条 wall 约 900–1000 秒，最后一条进入时第一条还没跑完，所以峰值驻留并发确实达到标称值。

两个刻意的选择，review 时别当成偶然：

- **20 秒错峰**：P 端同时叠 4–5 个长 prefill 会触发 deepgemm CUDA illegal address（5 秒错峰的 40 条实验 0/40 全灭，8 秒仍复现）。20 秒把这个独立问题隔离掉，让实验测的是 D 端容量和 decode 性能。代价是：本实验不能证明瞬发 32 条也稳定。
- **显式路由**：自然负载均衡的落点是 [5,4,4,4,4,4,4,3]，rank 偏斜让"每 rank 容量"没法下结论。显式路由消除偏斜，但也意味着没验证生产 LB 能不能自然摆出 4×8。

### 3.4 TPOT 口径（重要）

引擎的 `decode_service_us` 实际是完整 `cost_time_us`，包含首 token 之前的全部时间（`NormalGenerateStream.cc:164`）。直接除以 8191 会把 TTFT 摊进 TPOT，多算约 4.8–5.0ms/token。本文所有 TPOT 用修正口径：

```text
(decode_service_us - decode_first_token_us) / (output_len - 1)
```

原始 jsonl 里的 `steady_tpot_ms` 字段仍是旧口径，直接读原始数据时注意。

## 4. 结果

### 4.1 容量：A1 vs C，各 32 条

A1 和 C 唯一差别是 `V32_OFFLOAD_MODE`，同模型、同 runtime、同 12GiB D KV 预算。

| | A1（双池不 offload） | C（无损 offload） |
|---|---:|---:|
| 完成 | 8/32 | **32/32** |
| 实际峰值并发 | 1/rank | 4/rank |
| goodput | 62.98 tok/s | **165.86 tok/s（2.63×）** |
| TPOT mean（修正） | 100.02ms | 108.84ms |

A1 的 24 条失败全部是准入拒绝（0.23–0.26 秒返回 HTTP 500）：每条请求要 982 + 96(reserve) = 1078 块，第一条活跃后池里只剩 875–927 块，短缺 151–203 块。allocator 日志证据在 `rdma_a1_c_compare_20260904/A1_D_engine.log:348739-348742`。indexer 池当时还剩约 7191 块，完全不是瓶颈。

注意 A1/C 的 TPOT 差（+8.8%）**不是纯 offload 税**——两边实际并发不同（1/rank vs 4/rank），差值里混着并发影响。要提取纯税应比较同实际并发（A1-8 vs C-8：100.0 vs 102.4ms，约 +2.4%，但 A1-8 那轮的到达模式不完全对齐，只能参考）。

### 4.2 C 的并发趋势：8 / 16 / 24 / 32

每轮冷启动、清空 host mirror、同一 workload。数字已从原始 jsonl 独立复算核对过。

| 并发 | 每 rank | 完成 | TPOT mean | p95 | goodput |
|---:|---:|---:|---:|---:|---:|
| 8 | 1 | 8/8 | 102.375ms | 104.815ms | 61.6 tok/s |
| 16 | 2 | 16/16 | 106.769ms | 110.658ms | 104.6 |
| 24 | 3 | 24/24 | 108.249ms | 111.604ms | 138.9 |
| 32 | 4 | 32/32 | 109.802ms | 113.514ms | 165.6 |

8→32：TPOT +7.25%，goodput 2.69×。24→32 还有 19.25% 的吞吐收益，单请求代价只有 +1.43%——第 4 条/rank 仍然值得开。

### 4.3 多出来的时间在哪

breakdown 里 P compute（~26.7s）、normal load（~26.7s）、ring load（~1.1s）、admission prepare（~1.8s）、admission wait（0.004ms）全都不随并发涨。涨的只有首 token 之后的 decode 区间：838.6s → 899.4s（C8 → C32）。

C32 按提交波次拆 TPOT 也支持这个判断：第一波 111.9ms、第二波 110.6ms、第三波 109.3ms、第四波 107.4ms——越早进入的请求和后续请求重叠越久，TPOT 越高。这是 decode 并发饱和的形状，不是准入或传输成本混进来的形状。

但要诚实：目前的 breakdown 只能定位到"first-token 后 decode"这一层，还没有拆到 GPU kernel / batching / scheduler / PCIe fetch。说"符合并发竞争特征"可以，说"差值全部来自 batching"证据还不够。

### 4.4 正确性

四轮趋势实验 32/32 输出 hash 全部是 `27887e7c2b6b7b51`，与 A1 的 8 条一致。更早的 balanced32 有 2/32 hash 不同，但引擎本身就不是逐位确定的（MoE all-to-all 求和顺序，A vs A 都能 6 次 6 个输出，见 HANDOFF §9.2），所以 hash 一致是加分项，不是验收标准。验收标准是：完整输出 8192 token、无 allocator/CUDA/RDMA/lifecycle 错误、结束后 KV 全量归还、服务健康。四轮全过。

### 4.5 一个必须写清楚的限定

**A1=8 不是 H20 的硬件极限。** D 卡启动后还空着 22.75–23.89GiB，A1 失败是因为启动参数把 KV 硬限成 12GiB。正确的表述是：

> 相同 12GiB KV 配置下，C 把长请求容量从 8 条/node 提到 32 条/node。

如果把 D KV 提到 20GiB（按峰值余量估算仍安全），A1 容量会涨，对比需要重跑。

## 6. 已知问题，按优先级

1. **P 端 deepgemm illegal address**（4–5 个长 prefill 叠加即触发）。目前靠 20 秒错峰绕过，没修。它决定了系统能不能扛 burst。
2. **单机 A 并发 illegal address** 未定位。资源不足应该报错，不应该崩。
3. **pinned host 无预算控制**。每条 63k 请求约 4.8GB host mirror，C32 时 D 每 rank RSS 峰值 23.2GiB。没有池上限、没有 backpressure、没有分配失败的统一 rollback。上生产前必须补。
4. **AdmissionStore 的 block0 + generation 是补丁**，长期换 request_id + lease。
5. **normal load 和 host load 应合并成一次 tagged load plan**（省一个 cache-store round）。
6. 版本历史断档：9/2 的提交 `9ed432361`（独立 indexer 池）随损坏的 worktree metadata 丢失，本目录的未提交 diff 是它 + 之后 PD/并发工作的总和，基线是远程还能找到的 `5cb4bd891`。
