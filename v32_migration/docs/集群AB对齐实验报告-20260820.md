# DSV3.2 长上下文 A/B 对齐实验报告（2026-08-20）

**一句话结论**：staging 环准入机制已完整打通并修复三个深层 bug；但真正的第一杠杆是本次发现并修复的
**decode 8-rank 路由缺陷**（有效容量从 1/8 恢复到 8/8）——修复后 A 方案长请求成功率 3/128 → **85/128**，
而 B（环准入）在当前 63k@W48 对齐点为 39/128：**8 池空间足以吃下 A 的全量准入，B 的准入优势在此点
不兑现，反被传输税拖累**。B 的价值区间在更深的容量压力（W96/更高长比/128k 级请求），建议下一步在
该区间补判决。

## 2. 本轮交付的机制与修复

1. **Staging 环准入**（引擎 wheel，2 新文件+7 修改）：PD handoff 时长请求只分配
   block0+staging32+尾部 256+环 64=353 块（**与请求长度无关**，对照全量 63k=1030 块），
   16k 外前缀经环分批拉取直落引擎持有的 host 镜像+GPU indexer 池，python 侧 adopt
   （`ctx_adopt`，dlsym 通道）。设计文档：`staging-ring-admission-design.md`。
2. **decode 8-rank 分发修复**（`rtp_cluster.py::decode_worker_address`，配置级）：
   FlexLB 的 decode 候选从"每实例 1 端点(=rank0)"展开为每 DP rank 1 端点。
   **根因**：DP8 部署自上线以来只有 rank0 接请求，有效 KV 容量=名义 1/8——回溯解释了
   B2"单 rank 只容 7 并发长"、W96→W48 收益有限、"decode batch 全是 dummy 行"等全部历史现象。
3. **Master 块感知调度**（FlexLB jar `flexlb-api-blockaware-895edc9f`）：
   本地记账/in-transit 校正按 **offload 后驻留量**（`FLEXLB_DECODE_OFFLOAD_RESIDENT_TOKENS=24576`）
   而非全量 seqLen 估算长请求 KV 需求；decode 候选按"free KV ≥ 需求"软过滤——
   即"把 offload 释放的空间上报给 master"。
4. **三个深层 bug 修复**（各有独立判决证据）：
   - **镜像释放 UAF**（r2）：stream 结束即 free host 镜像而 fetch 线程仍在读 → 堆损坏
     （smoke 的 malloc_consolidate）→ 30s 墓地延迟释放；
   - **环拉取并发过载**（r4）：并发 5GB 级环拉取打爆 TCP cache store
     （Brm8：255×CACHE_STORE_PUSH_ITEM_FAILED，短请求也被拖垮）→ 每 rank 并发闸门（默认 1）；
   - **多 GPU 设备绑定**（r5）：gRPC 线程 current device=0 而 rank r 的池在 device r →
     ranks 1-7 全部镜像分配/搬运 invalid argument（Brm10 诊断：唯一成功的环拉取在 rank0）→
     入口按池指针 cudaSetDevice + RAII 恢复。修复后 Brm11 drain 失败=0、环拉取 20/26 完成。

失败码归因（关键行）：
- rank0-only 时代（A0m/B0m/Br0m）：长请求失败 ≈100% 为 `8211_DECODE_MALLOC_FAILED`（准入拒绝）。
  Br0m 的拒绝日志显示 need=353（cap 生效）但单 rank 空闲底线 150-453 < 353+reserve128——
  **准入策略无法在 1/8 容量的池上凭空造空间**（Br3m 用 4k 窗把长请求塞进去，反把短请求挤崩，总失败 44.7%）。
- Am8：长失败降为 40×8211（8 池下全量 1030 块也大多可入）。
- Brm8/9/10：8211 消失，改由 `CACHE_STORE_PUSH_ITEM_FAILED`（环拉取并发过载）+
  `drain enqueue failed`（设备绑定 bug）级联杀伤长短请求。
- Brm11：恢复到 49×8211 + 33×8207 + 80×短 514——过载显著缓解但仍有残余 store 压力。

## 4. 解读

1. **路由修复是数量级杠杆**：A 长请求 3→85（28×），总失败 13.7%→5.7%。此前所有 A/B 差异都
   被 1/8 容量遮蔽。
2. **对齐后的 A vs B（Am8 vs Brm11）：当前对齐点 A 胜**。
   63k 长请求 = 1030 块 = 单 rank 池的 42%；8 池分摊后 A 的全量准入大多能成立，B 的
   "353 块封顶"优势没有兑现空间，而 B 要为每个长请求付 ~5GB 环拉取传输税
   （长 TTFT p50 相当，但 store 压力挤伤短请求：10.6% vs 1.6%）+ 打分伺服税（TPOT 128 vs 108）。
3. **B 的价值区间**（待补判决）：a) 128k 级请求（A 需 2060 块=84% 单 rank 池，将重现饿死；
   B 仍是 353 块）；b) W96/更高长比（8 池水位整体抬高，A 的 1030 块窗口重新稀缺）；
   c) 秒拒→短重试窗的现实语义。B 机制本身已验证正确（环拉取 20+/26 完成、adopt 正常、
   全夜零崩溃——B6/B7 级联未再出现）。
4. **块感知调度**单项在本对齐点作用有限（Brm9≈Brm8），因为瓶颈在传输层而非调度估计；
   它的价值同样在高水位区间（防止 LB 按全量 seqLen 高估 offload rank 的占用）。

## 5. 遗留与下一步（按优先级)

1. **B 残余 store 压力**（Brm11 的 80×短 514 + 33×8207）：环限流已从 255 压到该水平；
   下一刀是环拉取批间限速/错峰，或 cache store 侧背压。
2. **在 B 的价值区间补对齐判决**：128k 合成 trace 或 W96/long50——预期 A 重新饿死、B 兑现常数准入。
3. **8211 残余（Brm11 49 长）**：块感知 LB 的轮询间隙仍可堆叠准入，可加 LB 预留记账
   （select 即预留、真值轮询清零）。
4. **工程收尾**：DP fanout 配置固化（含 A 线上）、V32AdmissionStore/环拉取上游 PR、
   长请求输出逐字正确性抽查自动化（本轮以 adopt/serve 计数+零 tripwire 为代理）。
