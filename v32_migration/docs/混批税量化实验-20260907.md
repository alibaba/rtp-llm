# 混批税量化实验

日期：2026-09-07

## 结论

在 cuda graph 关闭、8 条短请求与 1 条长请求固定落到同一 decode rank 的条件下：

- C 在纯短 batch 上有可观测的常驻 hook 税：**+1.383ms/token（+1.18%）**。
- A1 中混入一条原生长请求没有测到可分辨的 batching 税：点估计 **-0.080ms/token**，小于轮间波动，应视为 0 附近噪声。
- C mixed 相对 A1 mixed 的点估计是 **+0.676ms/token（+0.58%）**，但两轮分别为 +1.280 和 +0.072ms/token，C mixed 自身轮差 1.241ms 大于点估计。当前只能把 +0.676ms 当作观测中心，不能宣称已经精确量化出非零 offload 混批税。
- 完整生产形态 `C mixed - A1 pure` 的点估计为 **+0.595ms/token（+0.51%）**，同样处于当前噪声带内。

更重要的是，试跑发现 C 对 1,989-token 短请求存在确定性崩溃：`v32_capacity.py::_bookkeep` 固定申请 34 列并拷贝只有 32 列的 block table，触发 tensor 维度不匹配并带崩全部 D rank。正式实验将短 prompt 调整为 2,220 tokens（仍远低于 16,384 offload 阈值）后才通过。这个稳定性问题应先于性能优化处理。

## 实验矩阵

两机 Barex RDMA PD 部署沿用并发趋势实验：

| 项目 | 配置 |
|---|---|
| P | `11.17.131.204`，TP2×DP4，EP8，16GiB KV/卡 |
| D | `33.240.36.239`，TP1×DP8，EP8，12GiB KV/卡 |
| 固定 D rank | rank0，HTTP 27001 / gRPC 27002 |
| 公共参数 | `max_seq_len=73728`、`reuse_cache=0`、`enable_cuda_graph=0` |
| A1 | 双 KV pool，`V32_OFFLOAD_MODE=off` |
| C | `V32_OFFLOAD_MODE=capacity` + `V32_LOSSLESS=1`；这是当前 runtime 中 lossless C 的实际开关组合 |

正式四个条件：

| 条件 | 请求组成 | 目的 |
|---|---|---|
| A1 纯短 | 8 短 | 基线 |
| C 纯短 | 8 短 | 测纯原生 batch 上的 hook/wrapper 常驻税 |
| A1 混批 | 1 长 + 8 短 | 测原生 batching 影响 |
| C 混批 | 1 条触发 offload 的长请求 + 8 短 | 测 C 完整路径对短请求的净影响 |

每个条件跑两轮。A1 和 C 之间冷重启服务；同一方案内连续跑纯短两轮、混批两轮。C mixed 第一轮是 host mirror 冷分配，第二轮命中 mirror pool。

## 请求和时序

短请求：

```text
input_len=2,220
output_len=1,024
min_new_tokens=max_new_tokens=1,024
top_k=1
random_seed=1234
prompt SHA256=865d7c1d6d059f18de51691d269109a84cc781f2f176111d2c32cda75e339110
```

长请求：

```text
input_len=62,830
output_len=8,192
min_new_tokens=max_new_tokens=8,192
top_k=1
random_seed=1234
prompt SHA256=6f578b28135bd3901ee91def3209b1b3f62808a722e13da39e76a7286637361a
```

全部请求发到 P 的 HTTP 26100，并通过 `generate_config.role_addrs` 固定到 D rank0。混批轮在 `t=0` 提交长请求；短请求分两波提交：

```text
70, 72, 74, 76, 100, 102, 104, 106 秒
```

纯短轮使用完全相同的等待和短请求时序，只是不提交长请求。长请求 D first-token 为 25.75–26.92 秒，因此在第一条短请求提交前已经稳定进入 decode。worker_status 以 2 秒周期采样：纯短轮峰值为 8 条驻留；四个混批轮峰值均为 9 条，连续 43–44 个采样点处于 9 条共存，证明短请求 decode 与长请求 decode 充分重叠。

短请求 TPOT 使用修正口径：

```text
(decode_service_us - decode_first_token_us) / (output_len - 1)
```

## 正式结果

每格为一轮 8 条短请求的统计，单位 ms/token。

| 条件 | Round 1 mean / p50 / p95 | Round 2 mean / p50 / p95 | 合并 mean / p50 / p95 | 轮均值差 |
|---|---:|---:|---:|---:|
| A1 纯短 | 117.082 / 117.090 / 117.273 | 117.454 / 117.453 / 117.755 | **117.268 / 117.215 / 117.755** | 0.372 |
| C 纯短 | 118.955 / 118.884 / 119.570 | 118.347 / 118.335 / 118.456 | **118.651 / 118.463 / 119.570** | 0.608 |
| A1 混批 | 117.204 / 117.218 / 117.375 | 117.171 / 117.188 / 117.341 | **117.188 / 117.188 / 117.375** | 0.033 |
| C 混批 | 118.484 / 118.536 / 118.648 | 117.243 / 117.248 / 117.497 | **117.863 / 117.866 / 118.648** | 1.241 |

四个条件合计 64/64 条短请求成功，输出 hash 全部为 `47229f5fe1b12614`。四条长请求均完整输出 8,192 tokens，hash 全部为 `27887e7c2b6b7b51`。正式轮时间窗内没有 allocator、CUDA、RDMA、disconnect 或 mirror lifecycle 错误，结束后 P 和全部 8 个 D HTTP 入口均为健康状态。

## 税分解

| 指标 | Round 1 | Round 2 | 两轮点估计 | 判断 |
|---|---:|---:|---:|---|
| `(2)-(1)` hook 常驻税 | +1.873 | +0.893 | **+1.383ms（+1.18%）** | 两轮同号，差值大于各条件轮差；可以确认存在约 1ms/token 量级常驻税 |
| `(3)-(1)` 原生 batching 影响 | +0.122 | -0.283 | **-0.080ms（-0.07%）** | 符号翻转且小于噪声；未测到可分辨税 |
| `(4)-(3)` offload 净税 | +1.280 | +0.072 | **+0.676ms（+0.58%）** | C mixed 轮差 1.241ms 大于点估计；不能确认非零，只能报告范围 |

`C mixed - C pure` 的点估计反而是 -0.788ms。它不表示 offload 能加速短请求，而是再次说明当前两轮数据不足以解析亚毫秒级 mixed-only 增量。若要对 +0.676ms 做发布判决，需要按 A1/C 交错顺序做更多重复，而不是继续解释这两个点。

## 长请求参照

| 方案 | 两轮长请求 corrected TPOT | 均值 |
|---|---:|---:|
| A1 mixed | 114.784 / 114.695 | 114.739ms |
| C mixed | 115.409 / 115.088 | 115.249ms |

C 比 A1 高 0.510ms/token。C 两轮 ring load 为 963.6/930.8ms；admission blocking wait 都是 0.004ms。第一轮冷分配 4.78GB host mirror 用时 1,610ms，第二轮 pool hit 为 0.005ms；这些发生在 prefill/准入阶段，不计入修正后的短请求 TPOT。

D rank0 RSS 峰值从 A1 mixed 的 3.46–3.63GiB 增到 C mixed 的 8.24–8.35GiB，与一份约 4.78GB pinned mirror 一致。各条件 D GPU 整机平均利用率约 75.7–76.6%，显存峰约 117.5–118.0GiB，没有出现显存压力差异。

## 失败 pilot

最初按“约 2k”取了 1,989-token prompt。A1 四个 pilot 均成功，但 C 纯短第一条请求即触发：

```text
RuntimeError: The size of tensor a (34) must match the size of tensor b (32)
```

调用栈落在 `v32_capacity.py:338`：目标 buffer 固定为 `2 + STG_BLOCKS = 34` 列，而 1,989 tokens 只有 32 个 block-table 列。异常没有被隔离，导致全部 D rank 退出。证据前缀为 `PILOT1989_`，不参与正式统计。

## 后续优先级

在三项性能工作之前，先修短上下文 block-table 宽度问题。这个问题会使低于 MIN_SEQ、理论上不应进入 offload 的请求直接带崩 C 服务，优先级高于任何亚毫秒优化。

1. **Batch 级 fast path：最高优先级。** 在 Python 簿记和逐层处理之前，按 batch 判断是否存在 offloaded row。纯短 batch 应完全绕开 `_bookkeep`、`pre_topk` 和 per-layer process。它直接对应已确认的 +1.383ms/token 常驻税，也能规避本次发现的短 block-table 维度崩溃。
2. **Per-layer batched op：第二优先级。** mixed batch 只把 offloaded row 的索引传给一次 batched native op，不要让 8 条短 row 参与 Python/C++ 逐行判断。不过本次 mixed-only 税尚未从噪声中分离，实施前建议先增加可观测性并做 5 轮以上交错重复。
3. **CUDA graph 双版本 capture：第三优先级。** 本实验全程 `enable_cuda_graph=0`，没有测到 graph capture、graph break 或双图切换成本，不能用本报告为 graph 优化量化收益。应在 eager fast path 和 mixed batched op 正确稳定后，再分别 capture native-only 与 mixed/offload 两个版本。
