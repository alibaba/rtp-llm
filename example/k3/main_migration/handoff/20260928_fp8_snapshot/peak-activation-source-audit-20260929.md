# Peak activation: source audit before migration

This note records the fixed `feat/k3_dev` source at `a9bf762e878fc54ee9176da5c34ffbe6babc8d45` against the current integration branch at `b5a929bd339e542bdb814c1f84f015e26fbd5210`. It is a source and build-artifact audit, not a correctness or peak-memory measurement. Keep the planned performance anchor ahead of the peak-activation changes.

## Historical MLA KV expansion

The feat model reads `KIMI_K3_MLA_PREFILL_EXPANDED_KV_BUDGET_GIB`, defaulting to **6 GiB**, and passes it into the attention config ([model source, lines 25–43 and 344–346](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models/kimi_k3/kimi_k3.py#L25-L43)). The full-model smoke launcher also defaults to 6 GiB ([launcher, line 879](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/example/k3/kimi_k3_full_model_two_host_pd_smoke.sh#L879)). The budget is per rank because each rank constructs its own FlashMLA plan and workspace.

The planner keeps one full launch when the expanded total fits the budget, or when there is no historical prefix. Otherwise it aligns capacity to a physical prefix page and splits **historical prefix** into launches ([planner, lines 155–210](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/factory/attention/cuda_mla_impl/flashmla_forward_plan.py#L155-L210)). It does not cap the current query chunk's KV-up. The FP8 budget counts both the BF16 staging tensor and FP8 operand while they overlap ([dense Prefill, lines 627–637](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/factory/attention/cuda_mla_impl/flashmla_dense_prefill.py#L627-L637)). With the pinned K3 config's 96 heads, TP8, and `(128, 64, 128)` dimensions, that is 11,520 bytes per token per rank. A 6 GiB raw budget fits 559,240 expanded tokens before page alignment. Thus a 64K or 110K single request does not by itself exercise this splitting path; a smaller test budget is required. This arithmetic assumes the inspected four-layer checkpoint config and TP8.

The feat implementation reuses one workspace and gathers only the current historical slice for each launch ([dense Prefill, lines 122–205 and 1164–1230](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/factory/attention/cuda_mla_impl/flashmla_dense_prefill.py#L122-L205)). Its planner, packed-KV, FP8 MLA, and Page-RR NCCL tests already cover chunk planning, partial-state merge, and release of the previous canonical prefix chunk; these are the useful test starting points. The integration tree currently has no `flashmla_forward_plan.py` or `flashmla_dense_prefill.py`, so transplanting only the budget variable would have no effect.

## Skip-head-mid dependency

The feat MLA path uses a linear capability check for the `(128, 64, 128)` head layout, writes BF16 K/V around the empty RoPE region, then fills that region ([dense Prefill, lines 917–975](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/factory/attention/cuda_mla_impl/flashmla_dense_prefill.py#L917-L975)). The FP8 linear implementation calls `fp8_gemm_nt_skip_head_mid` into a caller-provided output buffer ([FP8 linear, lines 145–215](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/factory/linear/impl/cuda/fp8_deepgemm_linear.py#L145-L215)). Historical prefix launches reuse the packed output buffer. This is an actual GEMM output layout, not just a Python concatenation change.

The pinned integration DeepGEMM wheel `2.6.1+8bcfcab.cu132` exposes the **FP8** skip-head-mid symbol but lacks the **BF16** symbol in its runfiles `deep_gemm/__init__.py` and `_C.pyi`. The feat comparator build uses `2.6.1+72f2f3f.cu132`, which exposes both. The integration wheel pin is visible in [arch_config/arch_select.bzl, line 84](../../../../../arch_config/arch_select.bzl). The integration [DeepGEMM wrapper](../../../../../rtp_llm/models_py/kernels/cuda/deepgemm_wrapper.py) has neither skip-head-mid wrapper yet. Copying the feat wrapper wholesale would make its eager symbol resolution fail on the current integration wheel because `bf16_gemm_nt_skip_head_mid` is absent. FP8 skip-head-mid may be usable with the existing wheel, but its numeric behavior and speed still need direct tests. A BF16 route needs an explicit optional capability or a separately verified dependency update; do not silently fall back in the FP8 path.

## Other peak-memory candidates

The feat model owns an AttnRes bank sized for one local Prefill chunk and reuses it across rounds ([feat model, lines 1041–1077](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/model_desc/kimi_k3.py#L1041-L1077)). The integration [model](../../../../../rtp_llm/models_py/model_desc/kimi_k3.py) currently allocates `anchors` in `_forward_layers` for each invocation. Reusing this bank is a separate change from feat's chunk scheduler; measure both its persistent cost and request peak before deciding a capacity.

The feat MLA layer releases its historical-KV and merge workspace after attention consumes it and before its output projection ([feat model, lines 404–411](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/model_desc/kimi_k3.py#L404-L411)). The chunk session also releases the workspace before invoking the MTP draft hook ([feat chunk session, lines 1264–1270](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/kimi_k3/chunk_prefill.py#L1264-L1270)). The integration MLA uses a different wrapper and does not currently expose that release method. The release point must be checked against its output aliases and PD/MTP consumers before implementation.

The feat session drops the preceding target MTP hidden owner before the next target round ([feat chunk session, lines 1228–1236](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/kimi_k3/chunk_prefill.py#L1228-L1236)), with a model-owned release method ([feat model, lines 1026–1039](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/model_desc/kimi_k3.py#L1026-L1039)). The integration path passes hidden rows through `PyModelOutputs` and its [chunk-forward collector](../../../../../rtp_llm/models_py/modules/kimi_k3/chunk_forward.py); it has no equivalent model-owned buffer to clear. Measure the collector and draft consumer lifetime before adapting this idea.

The shared expert gate/up saving is **already present in substance** in the integration [MoE forward](../../../../../rtp_llm/models_py/modules/kimi_k3/moe.py): one BF16 projection returns a tensor whose two `chunk` outputs are views. The feat code uses the same single-output/view pattern ([feat MoE, lines 229–254](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/kimi_k3/moe.py#L229-L254)). This item needs a measurement of differing kernels or live ranges, not a duplicate migration.

Feat bounds collective GEMM workspace by one packed chunk ([feat utils, lines 60–80](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/rtp_llm/models_py/modules/kimi_k3/utils.py#L60-L80)) and sets `MEGA_MOE_MAX_TOKENS_PER_RANK=ceil(chunk_tokens/TP)` in its full-model launcher ([feat smoke launcher, lines 789–796](https://github.com/alibaba/rtp-llm/blob/a9bf762e878fc54ee9176da5c34ffbe6babc8d45/example/k3/kimi_k3_full_model_two_host_pd_smoke.sh#L789-L796)). The integration model already limits a single invocation through `chunk_prefill_budget=65536`, but its [MoE capacity calculation](../../../../../rtp_llm/models_py/model_desc/kimi_k3.py) still comes from `moe_prefill_max_tokens_per_rank` or `max_seq_len`. Before reducing workspace capacity, verify that all actual model entry paths, including MTP and Decode graph, obey the selected bound. This does not require transplanting feat's whole-model chunk scheduler.

## Required next evidence

Once 3FS reads recover, finish the FP8 Prefill performance selection and full-model smoke, then make the first anchor commit. For the peak phase, validate each migrated path on four layers first. Use a small historical-KV budget to force multiple launches, compare outputs with the unsplit route, and record both allocated and reserved GPU peaks. Check that current-query KV-up is reported separately from historical-prefix workspace. After the second anchor, repeat the planned full-model timeline and smoke; this audit alone establishes no performance or memory claim.
