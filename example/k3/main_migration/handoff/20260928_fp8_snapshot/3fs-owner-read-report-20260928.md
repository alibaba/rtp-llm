# Kimi K3 3FS 读取观察，供存储侧复核

时间：2026-09-28。客户端：L20-dev-110/112，挂载 `/mnt/hf3fs/3fs`，完整 target 为 96 个 shard、约 1.56 TB payload；RTP 通过 FastSafetensors SHM、`direct_io=True`、每 rank 2 GiB buffer、TP8 从该挂载直接加载。索引、shard header 和配置哈希均已核实。

1. 在 113 对完整 96 个权重文件做 **64 路 SHA256 读取加哈希**，3FS 源端 **236.379 秒**，同文件的本地 `/data0` **70.121 秒**，3FS 用时约为本地的 **3.37 倍**。这是读取加哈希口径，不是服务加载时间；缓存、CPU 和文件系统实现都会影响结果，不能称裸设备带宽。原始记录见 `3fs-storage-incident-20260927.md`。短时跨文件并发探针可达到更高的汇总吞吐，可能含服务端缓存，不能据此否定完整文件观察。
2. 正式 93 层 FP8 Prefill/Decode 的 target `load weights took` 分别为 **409.04/414.73 秒**。110 的八 rank、12 批 `copy_files` 累计约 211–252 秒，`get_tensor` 累计约 375–396 秒，两阶段流水重叠；`wait_queue` 累计约 5–24 秒，主要是首批。服务总启动更长，还包含 MoE 构造、MTP 加载和 CUDA Graph，不能算成 3FS 取数时间。
3. 为测试本机客户端并发瓶颈，只在 112 开任务独立 FUSE 挂载，将主 client I/O 线程 2→32、event loop 1→8、连接上限/并发 4→32，并将后台请求和 io_uring jobs 32→128。共享客户端、其他机器、集群配置未动。用同一 FastSafetensors SHM 路径、2 GiB buffer、八个不同 shard 并行，对照共享／高并发／共享的各 rank 读取中位数为 **18.178/18.481/18.634 秒**；没有可确认的改善。任务客户端已停止并卸载，配置哈希、日志和回滚记录见 `3fs-client-112-r33/`。
4. 110 的第二次完整加载在另一用户服务进入 GPU 时，某批 `copy_files` 最慢升至 51.02 秒，但下一些批次回到约 22–27 秒，且偏慢批次 `wait_queue` 约 0.04–0.07 毫秒。该次因 GPU 显存竞态 OOM，不是已证实的 3FS 故障。见 `r34-prefill-oom-110-20260928.md`。
5. 在 114 的空闲 GPU4 上，用只读 3FS 挂载、个人账号及任务临时容器，对同一 16.99 GB 四层 shard 比较 FastSafetensors SHM 的 bounce buffer。按 16 MiB／2048 MiB／256 MiB／2048 MiB／16 MiB／256 MiB 顺序，六次读取分别为 **20.450／14.570／17.396／13.600／16.209／17.624 秒**；首张量抽样和 5,404 个张量数一致。`read time` 均约 12.6–13.5 秒，差异主要来自 `copyToDevice`：2 GiB 为 0.99–1.89 秒，16 MiB 为 3.54–6.95 秒。正式 loader 已用 2 GiB，因此缩小 buffer 不是修复办法。每次仍出现 3FS SHM ioctl 的 `err22`，2 GiB 时各 10 条、16 MiB 时各 100 条；读取完成但应请存储侧解释该 ioctl 是否走了降级路径。原始逐次日志为 `fss-shm-buffer-114-gpu4.jsonl`，114 上的临时容器已自动退出。此六次交错读取是加载路径诊断，没有完成正式稳态基准所需的逐配置预热，不能据中位数推断长期吞吐。
6. 110 再次按原样从 3FS 直接启动完整 93 层 FP8 Prefill（r37）：target 各 rank `load weights took` 为 **416.98–432.42 秒**，MTP rank0 为 **39.72 秒**，总启动 **747.18 秒**。target 前 12 批 `copy_files` 每 rank 累计 **213.83–261.67 秒**，`get_tensor` 累计 **373.72–396.80 秒**；各批最大 `copy_files` **27.75–35.94 秒**。Prefill 与 112 Decode 的启动日志均通过 FastSafetensors 校验，无 loader fallback。以上是生产加载路径的独立观测，与文件读取加哈希和四层 shard 探针不能直接互换。
7. 110/112 的四层 FP8 PD 功能检查（r39）仍从同一 3FS 挂载直接加载 target；MTP 的本地 checkpoint 视图中，权重 shard 是指向 3FS MTP 目录的符号链接。Prefill rank0 target/MTP `load weights took` 分别为 **23.80/15.08 秒**，Decode 分别为 **45.34/20.18 秒**。随后 11 条 flow 请求全部完成，均有 PD 与 MTP draft 记录；这个功能结果不用于估算 3FS 读速。原始启动日志、配置和逐条请求保存在 `smoke-4layer-fp8-situ-r39-110112-20260928/`。
8. 为直接比较正式 SHM 读取路径，在 112 的独占 GPU0 上把同一个四层 shard（16,990,911,504 字节，SHA256 `807ec912…52e2b1d2f5ef9`）分别从 3FS 与本地 `/data1` ext4 交错读取，顺序为 3FS／本地／本地／3FS。两边均使用 `fast_safetensors.LoadWithShm`、`direct_io=True`、2 GiB buffer，得到相同的 5,404 个张量及首张量抽样值。每组独立进程先完成 3–4 次同路径预热，直到末三次落在中位数 ±5% 内，再保留其后的样本。两组 3FS 的样本中位数为 **14.241/13.889 秒**，两组本地为 **1.836/1.851 秒**；组中位数再取中位，3FS **14.065 秒**、本地 **1.843 秒**，约 **7.63 倍**。FastSafetensors 自身日志的稳态 `read time` 约为 13.5–13.9 秒对 1.48–1.51 秒，`copyToDevice` 两边均约 0.33 秒。3FS 每次读取出现 10 条 `err[22]`，本地没有。这个单 shard、热态路径对照解释了用户观察到的读取差异；每组有效样本仅 2–3 次，不能外推到全部 96 shard 的持续带宽或整模型启动。原始日志、GPU 主机选择、文件复制时间和分析结果在 `fss-local-ab-112/`，校验用的本地 shard 只放在 112 的个人数据盘。没有更改共享 FUSE 或集群配置。
9. 另一组早期诊断曾在 113 用 16 MiB SHM buffer 读取同一个四层 shard：`direct_io=True` 的后两次为 **15.61/16.16 秒**，`direct_io=False` 为 **30.88/31.83 秒**。这组试验没有交错顺序和正式稳态预热，buffer 也小于正式加载的 2 GiB；它只能说明该设置没有显示出立即提速，不能作为两种模式的最终性能比较。原始输出为 `fss-shm-directio1-113.log` 和 `fss-shm-directio0-113.log`。
10. 直接从 3FS 启动四层 FP8 双机服务，r40 的 target/MTP 加载耗时为 111 **26.01/15.16 秒**、112 **39.78/15.26 秒**；只改 MTP 投影后的 r41 为 111 **24.31/9.03 秒**、112 **45.60/12.99 秒**。两轮都通过启动日志的 FastSafetensors 正向校验，且权重配置与 shard 没有改变。四层服务加载时间有波动，不能把这几次差值归因于客户端调参或 modeling 变更。r40 的日志保存在 `smoke-4layer-fp8-gate-r40-111112-20260928/`；r41 启动日志仍在 111/112 的任务运行目录。
11. 为定位单文件串行读取是否受限，在 113 对同一个四层 shard 做只读 `O_DIRECT`、4 MiB 对齐分片扫描，每个线程读取不重叠的块，完整读取 16,986,931,200 字节；线程数按 1→8→32→64→32→8→1 往返。对应吞吐为 **945/6444/19065/29214/19251/6421/919 MiB/s**，所有轮次的分片抽样校验和一致。这证明该客户端和路径在这次热态探针中能通过同文件并发大幅提高汇总读取速度，单线程却仍约 0.9 GiB/s。64 线程值可能受到服务端缓存影响，且这是原始 `preadv`，不是 FastSafetensors SHM、更不是完整模型加载吞吐。原始记录和只读脚本分别为 `bench-3fs-single-shard-direct-parallel-113.jsonl`、`bench_3fs_single_shard_direct_parallel.py`。未调整任何客户端或集群配置。
12. 随 Bazel 使用的 `fast_safetensors` Python `interface.py` 虽然定义了 `load_safetensors(path, num_threads=...)`，当前 0.7.3 二进制扩展却没有 `_C.load_safetensors`，调用直接 `AttributeError`，因此不能用这个表面上的线程数参数替换正式 SHM loader。113 上同 shard 的 `load_safetensors_to_device(..., use_shm=False, direct_io=True)` 单次读耗时 **15.92 秒**，内部打印 `read[14838]` 毫秒；这条非 SHM 路径也未显示出自动多线程提速。测试仅一轮、GPU7 上还有另一个用户的空闲进程，不能视为独占稳态性能数据；这里只用来排除明显的替代加载接口。脚本 `bench_fast_safetensors_device_path_113.py`。
13. 系统调用跟踪证实同一 shard 在 SHM ioctl `EINVAL` 后由一个线程发起 510 次 `pread64`，499 次为 32 MiB。只在任务进程使用、可通过移除 `LD_PRELOAD` 回滚的 64 线程并发读取原型，令 113 上同一 FastSafetensors SHM 单 shard 的完整加载中位数从 **18.894 秒**降为 **4.799 秒**，内部 `read` 从 **16.970 秒**降为 **2.436 秒**；5,404 个张量的完整字节摘要相同，同一 reader 切换到大小相同的另一个 shard 也核对通过。111 实际四层 TP8 Prefill 的 rank0 target/MTP `load weights took` 为 **12.33/7.91 秒**，原 r41 为 **24.31/9.03 秒**，FastSafetensors guard PASS。原型、原始日志、启用/回滚和内存风险见 `3fs-parallel-pread-prototype-20260928.md`。这只是任务局部绕开串行取数的诊断办法，尚未成为 FastSafetensors/3FS 的正式修复；也没有把设置扩展到全部 110–115。
14. 继续测试更高并发：113 对同一 shard 的热态 `O_DIRECT` 分片扫描，在 64／128／256／512／1024 线程下分别测到约 28／32–40／38–42／32–33／20 GiB/s，256 线程是这组原始读取的最高点，所有轮次抽样校验和一致。随后在 114 空闲 GPU4、可读 3FS 的同镜像个人容器中，用真实 FastSafetensors SHM、`direct_io=True`、2 GiB buffer 和任务级并发库比较 64／128／256 线程。两次内部 `read` 分别为 **2.192/2.123、2.138/2.129、2.092/2.227 秒**；继续加线程没有可确认收益。整次加载分别为 **4.341/5.920、8.773/6.381、6.232/6.170 秒**，GPU 拷贝和初始化的波动更大。这是两轮交错的加载路径诊断，未按正式性能基准完成逐配置预热；不能把原始分片扫描峰值当作 FastSafetensors 吞吐。原始记录为 `bench-3fs-max-concurrency*-113-20260928.jsonl` 和 `fss-114-{64,128,256}-*.log`。113 上另一次没有 `O_DIRECT` 的简化 256 线程 `pread64` 进程超过两分钟未完成，已只终止该任务进程；它与正式加载路径不同，仅提示不能盲目提高并发。当前任务进程仍使用 64 线程，上限没有推广到其他机器。

检查当前随 Bazel 构建的 FastSafetensors `parallel_loader.py`：`iterate_weights()` 只启动一个 producer 线程；该线程顺序调用每批的 `copy_files_to_device()`。`max_concurrent_producers` 虽然作为参数保存，当前代码没有按它创建更多 worker。`max_threads` 只进入 nogds copier，正式 SHM 路径不使用它。底层 `fast_safetensors.LoadWithShm` 构造器只接受 buffer、device、direct I/O 和 NUMA 参数，没有读取线程数。四层 target 只有 7 个 shard，TP8 的文件分批方式至多让 7 个 rank 同时读取不同文件。若要提高正式加载的有效文件并发，需要验证加载器、底层 SHM copier 和显存生命周期的改动，不能仅把现有配置数字调大。

希望存储侧协助确认：同文件的 SHM 直读为何比本地 ext4 慢约 7.6 倍，`set/copy to shm` 的 `err[22]` 是否触发降级；完整文件顺序读为何仍比本地数据盘慢约 3.37 倍；SHM/direct-I/O 下每个 rank 对单 shard 的服务端吞吐、缓存命中、RPC 排队、RDMA/网络和客户端限流；能否在**不修改共享/全局配置**的前提下提供针对任务读取的更有效并发参数或路径。当前没有证据支持把本次 32 线程配置推广到所有机器。模型加载时大量读取与权重处理重叠，因此修复文件读取速度与缩短端到端模型加载需分别验证。

64 线程任务级原型在单 shard 上明显缩短了读取时间，但还没有完整 93 层、多 rank 稳态结果，也不是 FastSafetensors 或 3FS 的正式修复。开发中继续直接读 3FS，优先用四层权重验证，并在代码未改变时复用已加载服务，以减少重复加载。
