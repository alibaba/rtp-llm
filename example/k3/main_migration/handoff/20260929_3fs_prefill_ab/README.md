# Four-layer FP8 Prefill A/B on 114/115, 2026-09-29

This is an interim measurement record, not the performance anchor. The integrated RTP service used the four-layer K3 checkpoint, TP8/EP8 PD, FP8 target weights and MLA, BF16 NCCL, and Native MTP. Both roles loaded the verified checkpoint directly from 3FS through FastSafetensors. The task process used 64 parallel pread workers. In the matching FastSafetensors test, 128 and 256 workers did not shorten the read stage, so 64 is the highest *effective* setting observed for this loader. No cluster-wide 3FS setting was changed. The local data-disk copy remains the fallback if 3FS reads fail or slow materially.

The A/B used the same 114 Prefill and 115 Decode hosts, 65,536 submitted token IDs (SHA256 `97a53100491426d80436747b477dbe592ea1106eed6308a99ab83ba1bd3863ee`), eight generated tokens, and full-rank traces. The integrated runtime model code came from `869efba9652ee9cc3f4e7abcca1d372b8e31b11e` with local launcher/test fixes equivalent to the later `ffff64c99eac2db767c36288c54f04a741350c17`; the fixed comparison branch was `feat/k3_dev@a9bf762e878fc54ee9176da5c34ffbe6babc8d45`. The integrated run had 12 stable warmups and 16 successful profiled requests. The fixed `feat` run had 11 stable warmups and 16 successful profiled requests. Both eight-rank traces contain target and draft forward scopes for each of the eight sampled requests. The integrated request audit also reports Decode PD handoff and positive MTP draft rounds.

The numbers below are medians over eight requests of the **maximum rank** GPU timing for each request, in milliseconds. A span includes gaps between kernels; union is time during which at least one GPU kernel ran on that rank.

| Phase | Integrated span | Fixed `feat` span | Integrated union | Fixed `feat` union |
| --- | ---: | ---: | ---: | ---: |
| Prefill target + draft | 134.847 | 132.082 | 127.936 | 129.431 |
| Target | 71.611 | 70.946 | 67.366 | 69.210 |
| Draft | 63.387 | 60.624 | 60.539 | 60.070 |

The integrated target ran fewer cumulative GPU kernel milliseconds, but its target span was 0.665 ms longer; its complete Prefill span was 2.765 ms longer. The current trace points to launch gaps around input preparation and the target/draft boundary. This is a diagnosis, not proof of a safe optimization. Source-backed attribution of the stable rank samples found near-equal KDA and MLA core kernel time, while the integrated routed MoE kernel total was lower (14.271 versus 15.939 ms). Labels and fusion boundaries differ, so the table cannot establish a winner for every operation. Some fixed `feat` target collectives use FP8 value/scale communication, which does not meet the BF16 NCCL contract for the integrated version. The fixed branch also computes 65,533 of the 65,536 submitted Prefill tokens in this trace. These two differences limit end-to-end interpretation.

I tried constructing the MTP verify reserve-prefix metadata on the host. A small isolated hot microbenchmark improved, and an 11-case four-layer PD flow passed, but the same-host 64K PD trace got slower: 135.368 ms complete Prefill span and 71.749 ms target span. I reverted the candidate. `rejected-mtp-host-reserve.patch` is retained only to explain the experiment and should not be applied as a performance change.

`integrated-r2-114115.tar.gz` and `hostreserve-r3-114115.tar.gz` contain all eight rank traces, all warmup and profiled responses, independent request audits, phase-correlation audits, and module attribution. `hostreserve-flow-r5-114115.tar.gz` contains the 11-case flow and its independent audit. `summary.json` records the precise timing values, SHA256 digests, and further limitations. The fixed `feat` trace and its flow evidence are already under `../20260928_fp8_snapshot/evidence/kmerge-20260929/feat-r12-114115/`; the pinned vLLM target-only NIXL PD record is under `../20260928_fp8_snapshot/evidence/vllm_3df4_r2/`. That vLLM run has no Native MTP and uses MXFP4 routed MoE, so its target span is a diagnostic rather than a direct all-model comparison. Four-layer random outputs and these timing runs do not replace final 93-layer answer validation.
