# 双层真实 Engram lookup：Nsight 诊断结果

**本轮为 PROFILE_ONLY，不能用于替代正式 SLO 测试。** M=1、两层完整表、同一 GPU 顺序执行两次独立 lookup，比较本机 host-pinned 和跨机 EGM。只覆盖已有 IDs 到 BF16 查表输出，不包含 hash、WKV、gate、模型层间计算或 HTTP decode。

这轮没有复现上一轮的 GPU 毫秒级长尾；墙钟仍有 18 对正增量超过 100 µs。当前 trace 可以定位这些墙钟异常落在哪个区间，但不能据此宣布原问题解决，也不能归责 fabric、网络、操作系统或 profiler。

## 数据与关联校验

- 10,000 个配对样本，20,000 次调用、40,000 条 raw 时钟记录；重新计算的四组绝对耗时和两组配对增量统计均与原 summary 一致。
- 20,000 个精确 NVTX label → 20,000 次成功 Graph launch → 40,000 个 `_lookup_host_kernel`，每次调用恰好两个；20,000 次 completion API 也均关联，未解析条目为 0。
- 另外 20,000 个 add kernel 属于计时前的 scratch 扰动，逐个确认在 NVTX 区间外。scratch 是 runtime L2 的两倍；这**不保证真正冷缓存**。
- 实际 Graph 输出在计时前后均做 oracle 校验，profiler Start/Stop 成功，结束时八项 native resource counter 全为 0。
- 仍有四条采集警告：MMAP 符号信息缺失，以及 CUDA、NVTX、OS-runtime 事件可能未全部采集。公开 JSON 仅保留警告类型及脱敏内容；原始 trace 留在私有证据中。这里只认证已知 20,000 次关联，不宣称全局 trace 无缺失。

### pair 5893：约 104 ms 的墙钟异常

remote 原始墙钟为 103,975.703 µs，其中提交调用为 103,922.551 µs，同步调用为 53.152 µs；local 墙钟为 152.160 µs。remote 的 Graph event 为 50.912 µs，两次 lookup 分别为 9.664/9.088 µs，间隔 0.160 µs。

Nsight 同一条 NVTX range 开始到第一次 CUDA API（`cudaStreamIsCapturing`）约 103,728.150 µs；Graph launch API 本身只有 136.928 µs。因此这次长墙钟不对应同量级的 lookup kernel 延长，也不主要发生在被记录的 Graph launch API 内。NVTX 包围范围比 raw 墙钟稍宽，二者没有强行对齐时间原点。

raw 记录一次 involuntary context switch；同一线程、同一 NVTX 区间里记录到一组 sched-out/in，间隔 **66.496 µs**。它不能解释约 103 ms 的全部停顿。该区间没有已记录的 OS-runtime API；结合采集警告，不能把“未记录”解释成“必然没有”。具体成因仍未定。

### pair 3539 / 6968：同步返回慢，lookup 本身短

remote `cudaEventSynchronize` 在 trace 中分别为 852.867 / 539.682 µs；最后一个 lookup 结束到该 API 返回分别相隔 843.507 / 527.794 µs。两次调用的 lookup span 分别约 18.080 / 17.248 µs。raw 两侧 context-switch 计数均为 0，trace 中也没有对应已记录的调度或 OS-runtime 事件。证据定位到 completion 路径的返回延迟，尚不能进一步判定原因。

### 最大 GPU event 增量：pair 1988

配对增量为 34.112 µs：remote event 56.448 µs、local event 22.336 µs。remote 两节点仅 7.744 / 7.936 µs，间隔 0.160 µs，Graph launch API 为 46.976 µs。event 减 kernel span 的 40.608 µs 是两种 instrumentation 的区间差，**不是已经定位到的 GPU 节点间隙**；没有 event-node 时间线证据，不能把这部分指认为具体原因。
