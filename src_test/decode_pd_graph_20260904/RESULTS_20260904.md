# DECODE PD-fusion + CUDA Graph sCR 实验（2026-09-04）

## 目标和固定条件

本轮验证 DECODE 进程（PD fusion 的 decode 侧）在 CUDA Graph 开启时是否能执行 sCR GPU-only dump/restore。运行时变量如下：

```text
模型：/tmp/models/DeepSeek-V4-Flash-0731
RTP-LLM Python：/opt/conda310/bin/python3
Epsilon effective implementation：/etc/scr/epsilon/__init__.py
SCR_ENABLE=1
RTPLLM_ENABLE_SCR=1
SCR_PHASE=checkpoint
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:False,large_segment_size_mb:1024
sCR scheduler：/home/yuziqu.yzq/scr_scheduler --fork false --safe-block-backoff 5
```

`/home/yuziqu.yzq/scheduler_config.json` 与 `/run/scr/config.json` 未修改，内容为：

```json
{
  "bypass_dump_restore": true,
  "log_level": "info",
  "crc_check": true,
  "log_exporter": "uds_file",
  "bounce_buffer": true,
  "cache_fs_sock_path": "/run/cachefs/cachefs-api.sock"
}
```

`bypass_dump_restore=true` 只验证 scheduler 的 GPU bypass 内存路径；本实验不执行 CPU dump，也不执行 CRIU 进程 checkpoint。

## 角色配置

| 角色 | GPU | 端口 | 并行度 | CUDA Graph |
|---|---|---:|---|---|
| DECODE | 0,1 | 18530/18531 | tp=1, dp=2, ep=2, world=2 | 开启，capture 1/2/4/8/16 |
| PREFILL | 2,3 | 18630/18631 | tp=2, dp=1, ep=2, world=2 | 关闭 |

统一启动脚本是 [`launch_pd_fusion.sh`](launch_pd_fusion.sh)。它设置 `BASE_WORK_OVERRIDE` 后即可把运行日志放到独立目录：

```bash
BASE=/dev/shm/rtp_llm_decode_pd_graph_20260904_run
mkdir -p "$BASE"
sudo -n env BASE_WORK_OVERRIDE="$BASE" setsid -f \
  bash src_test/decode_pd_graph_20260904/launch_pd_fusion.sh decode \
  > /tmp/decode_pd_graph.launch.log 2>&1
sudo -n env BASE_WORK_OVERRIDE="$BASE" setsid -f \
  bash src_test/decode_pd_graph_20260904/launch_pd_fusion.sh prefill \
  > /tmp/prefill_pd_graph.launch.log 2>&1
```

启动日志确认 DECODE 的 `enable_cuda_graph: 1`、5 个 capture batch size 和 PREFILL 的 `enable_cuda_graph: 0`。8 个 Epsilon participant（backend、rank、frontend、dash-sc）均记录 `snapstart_checkpoint ... success` 并进入统一 barrier。

## PD-fusion 请求

DECODE backend 本身不实现普通 `GenerateStreamCall`，因此必须通过无 GPU frontend gateway 路由。gateway 脚本为 [`launch_gateway.sh`](launch_gateway.sh)：

```bash
setsid -f bash src_test/decode_pd_graph_20260904/launch_gateway.sh \
  > /tmp/decode_pd_graph.gateway.log 2>&1
curl -fsS http://127.0.0.1:18730/health
curl --max-time 600 -sS \
  -H 'Content-Type: application/json' \
  --data-binary @src_test/decode_pd_graph_20260904/request_pd.json \
  http://127.0.0.1:18730/v1/chat/completions
```

本轮返回 HTTP 200，核心结果如下（输出为 `ok.`）：

```json
{
  "usage": {"prompt_tokens": 12, "total_tokens": 14, "completion_tokens": 2},
  "aux_info": {
    "pd_sep": true,
    "role_addrs": [
      {"role": "DECODE", "http_port": 18530, "grpc_port": 18531},
      {"role": "PREFILL", "http_port": 18630, "grpc_port": 18631}
    ]
  }
}
```

这里 `max_tokens=2` 是有意的：`max_new_tokens=1` 会走 PREFILL 本地生成旁路，不能证明远程 DECODE；`pd_sep=true` 才是本轮 PD-fusion 入口证据。

## GPU-only dump 过程

本轮使用的 checkpoint 目录是：

```text
/dev/shm/rtp_llm_decode_pd_graph_20260904_dump
```

实际命令与脚本等价：

```bash
sudo -n /home/yuziqu.yzq/scr_controller check
sudo -n /home/yuziqu.yzq/scr_controller dump \
  --path /dev/shm/rtp_llm_decode_pd_graph_20260904_dump \
  --bypass-cr-path /dev/shm/rtp_llm_decode_pd_graph_20260904_dump \
  --block-timeout-ms 120000
sudo -n /home/yuziqu.yzq/scr_controller wait-cr-done --timeout 1800
```

也可以运行 [`dump_restore_gpu_only.sh`](dump_restore_gpu_only.sh)；`wait-cr-done` 按 controller 1.6.0 的实际接口只传 `--timeout`，不会误传 path 参数。

### Dump 结果

- controller 的 `dump` RPC 返回 `dump_rc=0`。
- scheduler 日志确认 8 个 Aion client 的 `SchedulerApi::Dump` 均为 `success`，并记录 `SchedulerApi::Dump Done`。
- 目录产生 8 个文件，其中 4 个元数据文件和 4 个大 GPU 文件；大文件 apparent size 约 343G，tmpfs 实际占用约 160G。
- dump 后所有 participant 执行 `CloseFd`，GPU context/resource cleanup 完成；应用 TCP listener 一度仍存在，但 gRPC keepalive 随后报告 transport closed。

关键原始证据：

```text
/home/serina.wzq/test/decode_pd_graph_20260904/dump.controller.log
/run/scr/log/scheduler.log                  # 约 09:13:30 的 Dump/CloseFd 链路
/dev/shm/rtp_llm_decode_pd_graph_20260904_dump/
```

## 为什么本轮没有完成 restore

dump 过程中机器内存达到上限。旧实验数据位于 `/tmp/test`（约 740G tmpfs），本轮 dump 位于 `/dev/shm`（约 160G tmpfs）；`/proc/meminfo` 的 `Shmem` 达到约 899G。内核记录：

```text
Out of memory: Killed process 1730553 (scr_scheduler)
  total-vm:760879872kB anon-rss:8388608kB shmem-rss:166017024kB
```

随后原 scheduler 的 ttrpc 连接返回 `Connection refused`。我在只读检查后重启了同一参数 scheduler，它重新发现 8 个 Aion socket；但是 `wait-cr-done` 的持久化阶段返回：

```text
Failed to find the original rund-cr-scheduler in pkg dir
```

随后开始执行：

```bash
sudo -n /home/yuziqu.yzq/scr_controller restore \
  --path /dev/shm/rtp_llm_decode_pd_graph_20260904_dump \
  --bypass-cr-path /dev/shm/rtp_llm_decode_pd_graph_20260904_dump
```

但用户要求先把脚本和文档提交保存，restore 命令在收到响应前中止；[`restore.controller.log`](/home/serina.wzq/test/decode_pd_graph_20260904/restore.controller.log) 只记录了连接开始，没有 `restore_rc`。因此本轮结论是“PD-fusion + CUDA Graph + GPU dump 已复现”，不是“完整 restore 已成功”。

## 复现时的注意事项

1. 先检查 `df -h /tmp/test /dev/shm`；不要在两个接近满载的 tmpfs 上同时保留多份大 checkpoint。
2. 保持 `/home/yuziqu.yzq/scheduler_config.json` 不变；本轮使用的 `--safe-block-backoff 5` 是 scheduler CLI 固定条件。
3. 只使用 `check -> dump -> wait-cr-done` 的 GPU 流程；不要把 `wait-cr-done` 的 rund-cr-scheduler 错误解释成 GPU Dump RPC 失败。
4. 运行 restore 前，确认 scheduler 进程仍为 live、ttrpc socket 能连接、8 个 participant 没有退出，并记录 restore 后的端口、Epsilon 日志和再次的 `pd_sep=true` 请求。
